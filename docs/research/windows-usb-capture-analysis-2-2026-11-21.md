# Windows USBPcap capture analysis #2, azul root-hub capture, 2026-11-21

Source file: `re/captures/usbcap-azul-root2-2026-11-21.pcap`, same root hub and session as the prior capture analyzed in `windows-usb-capture-analysis-2026-11-21.md`. Per the task context, this file was taken while a `pnputil` disable/enable attempt against the dock's composite device ran, but that attempt failed to apply live and required a reboot, so this file is treated here as a longer steady-state window, not a verified enumeration trace. No `tshark`/`capinfos`/`editcap`/Scapy/dpkt were available on this host, so all facts below again come from a hand-rolled Python struct-level USBPcap parser (kept under the scratch cache, not in this repo), independently re-run multiple times against different fields for cross-checking.

## Result

The file is a 71.196-second capture (first timestamp 1795265152.484243, last 1795265223.680374) containing 178,747 USBPcap records, far larger than the prior 227 ms / 493-record file. The same eight device addresses from the prior capture (16, 21, 23, 24, 26, 29, 30, 35) are present continuously across the entire 71 s window with no gaps, confirming the dock's own addresses did not drop off or re-enumerate during this capture, consistent with the task's statement that the `pnputil` action did not apply live. Eight additional, previously-unseen addresses appear (4, 5, 14, 15, 28, 36, 37, 38), but all of them are short-lived, clustered in a roughly 12-second window (first seen 44.57-44.74 s, mostly gone again by 46.8-56.1 s), and their decoded descriptor strings identify them as unrelated hub peripherals (a HyperX QuadCast microphone, a CORSAIR mouse/headset/lighting-node/wireless-receiver set, a Dell presence sensor, a ZSA Moonlander keyboard, and two generic "HID Device"/"HID Interface" placeholders) rather than the dock.

The device-35 H.264 finding is reinforced in its core shape (constant leading byte 0x02, endpoint 2, interrupt-OUT, 4096-byte reports) but is refined by a much larger sample: of 2,017 such reports, 1,579 carry exactly one H.264 NAL (type 1, non-IDR slice) starting at a fixed byte offset, only 6 carry a full three-NAL keyframe group (types 7=SPS, 8=PPS, 5=IDR slice), and 383 carry no NAL start code at all. The device-23 control-transfer pattern also repeats, but turns out to be a steady ~0.51-second periodic poll (139 identical request/response pairs), not a one-off handshake. Unexpectedly, this capture does contain real USB descriptor exchanges (GET_DESCRIPTOR, STRING type), something the prior capture had zero of, but every decoded string belongs to a non-dock peripheral or is a generic placeholder; no DEVICE or CONFIGURATION descriptor, and no idVendor/idProduct bytes, were requested or found anywhere in the file.

Record/transfer-type totals: 178,747 records parsed cleanly to end-of-file (no truncation). Transfer-type counts: INTERRUPT 161,939, ISOCHRONOUS 14,240, BULK 2,012, CONTROL 540, plus 16 records carrying a non-standard transfer-type byte (0xFE) that correspond one-to-one with URB function `0x001E` (`URB_FUNCTION_SYNC_RESET_PIPE_AND_CLEAR_STALL`, a non-data-transfer URB with `dataLength=0`); direction counts OUT 91,815 / IN 86,932. URB function-code counts: `0x0009` (BULK_OR_INTERRUPT_TRANSFER) 163,951, `0x000A` (ISOCH_TRANSFER) 14,240, `0x0008` (CONTROL_TRANSFER) 409, `0x000B` (GET_DESCRIPTOR_FROM_DEVICE) 126, `0x001B` (CLASS_INTERFACE) 5, `0x001E` (SYNC_RESET_PIPE_AND_CLEAR_STALL) 16. GET_DESCRIPTOR(STRING) decode: every `0x000B` setup packet decoded (`bmRequestType=0x80, bRequest=0x06`) asks for descriptor type 3 (STRING), never type 1 (DEVICE) or type 2 (CONFIGURATION). Decoded UTF-16LE string payloads from the immediately-following IN data-stage record, by device: dev 14 index 2 = "HyperX Quadcast"; dev 15 index 2 = "Moonlander Mark I"; dev 16 index 2 = "CORSAIR DARK CORE RGB PRO Gaming Mouse"; dev 24 index 2 = "CORSAIR Lighting Node CORE"; dev 26 index 6 = "Commander PRO"; dev 28 index 2 = "Corsair ST100 Headset Output" (one byte in the raw descriptor, 0x1c, is a mid-string low-value byte that decodes to a non-printable UTF-16 code point, most likely a single corrupted/mis-aligned byte in this instance of the descriptor rather than a parser bug, since the surrounding characters decode cleanly); dev 29 index 2 = "Corsair ST100 LED Driver"; dev 30 index 2 = "CORSAIR Slipstream Multi-Device Receiver"; dev 35 index 5 and index 7 = "HID Interface" (both indices return the identical generic string); dev 37 index 2 = "Dell Presence Sensor WB7022"; dev 38 index 2 = "HID Device". The GET_DESCRIPTOR burst (126 records) spans t=44.73-46.79 s, directly overlapping the SET_IDLE cluster and the first-seen times of the new addresses.

Device-23 control-transfer repeat: every one of the 278 records on device 23 is one of exactly two fixed payloads, `c0 05 08 e9 03 01 04 00` (setup; decodes to `bmRequestType=0xC0, bRequest=0x05, wValue=0xE908, wIndex=0x0103, wLength=0x0004`, identical to the prior capture) or `84 00 ff ff` (4-byte response), alternating 139 times with inter-request intervals consistently ~0.50-0.515 s (sampled: 0.509, 0.509, 0.509, 0.509, 0.515, 0.513, 0.514, 0.512, 0.515, 0.500 s across the first ten repeats).

Device-35 H.264 payload re-scan: endpoint 2, interrupt-OUT, 4096-byte reports total 2,017 (plus 2,017 matching 0-byte completion records). Byte 0 is `0x02` in all 2,017 cases (unchanged from the prior capture). First Annex-B start-code (`00 00 01`) offset distribution: 1,584 at offset 17, 41 at offset 1, 7 at offset 14, 2 at offset 15, and 383 with no start code found anywhere in the 4096-byte payload. NAL-type sequence (first up to 4 start codes per payload, NAL header low 5 bits) distribution: `(1,)` i.e. a single non-IDR slice NAL, 1,579 occurrences; `()` i.e. no NAL at all, 383; `(7, 8, 5)` i.e. SPS, PPS, IDR-slice, 6 occurrences; a long tail of rarer single-digit-count sequences including `(0,)`, `(18,1)`, `(6,1)`, `(9,1)`, `(19,1)`, `(30,1)` (types 0, 6, 9, 18, 19, 25, 30 are non-slice/non-parameter-set NAL types or reserved/unassigned values and are treated as either auxiliary NAL units or coincidental byte matches, not verified as meaningful without a real H.264 decoder). Sampling the first 17 bytes of frames spaced ~200 apart across the whole file shows bytes 0-3 constant (`02 00 00 00`), byte 4 varying (observed `c2, cc, ed, d3, d0, bf, a9, 91, c3, 00`), byte 10 constant `05`, bytes 11-13 constant `00 00 00`, bytes 14-15 constant `02 d0` (=720 decimal, matching the 1280x720 frame size already inferred from the Mac-driver Ghidra analysis), byte 16 constant `00`, followed by the Annex-B start code at byte 17 in the majority case. (Two of the ten sampled frames break this pattern entirely -- at t+~27 s and t+~34.5 s the bytes after the leading `02 00 00 00` are all zero and no start code appears until deep in the payload -- consistent with the 383 no-NAL-found reports noted above, i.e. idle/no-new-frame reports.)

## Interpretation

This longer window reinforces the device-35 H.264 finding's core transport shape (constant 0x02 leading byte, fixed endpoint, fixed 4096-byte report size) but shows the prior capture's 10-sample characterization (every report = SPS NAL immediately followed by a slice NAL, with the SPS starting right after the single leading byte) was an artifact of its small sample. With 2,017 samples here, the dominant pattern is a single non-IDR slice NAL per report (1,579 of 2,017), preceded by what looks like a fixed-layout ~17-byte packetizer header (not raw Annex-B from byte 1) whose byte-14/15 field is constant at the decimal value 720 across every sampled frame and whose byte-4 field varies frame to frame -- plausibly a per-frame size or sequence field, though this parser cannot confirm that without decoding the actual NAL payload lengths. A full three-NAL SPS+PPS+IDR-slice keyframe group (what a real decoder would need to start a GOP) does appear, but rarely (6 of 2,017, roughly once every ~12 s of a presumably mostly-static test screen), and 383 reports (19%) carry no detectable NAL at all, which looks like idle/keep-alive or no-new-frame reports rather than video data. None of this changes the identification of the traffic as H.264 Annex-B chunked into fixed-size HID-shaped OUT reports; it corrects the earlier small-sample claim that every report contains an SPS, and it adds a plausible structured header field (constant 720) that the prior analysis did not have enough samples to notice.

The device-23 control transfer is now firmly reinforced as periodic polling, not a handshake: 139 byte-for-byte identical request/response pairs at a steady ~0.51 s cadence across the whole 71 s window rules out the "one-off handshake" reading the prior capture could not rule out, and instead points to this being a status/heartbeat poll (e.g. a link-state or button-state register read) that runs continuously once the device is up, independent of anything resembling enumeration.

The eight new device addresses are not new dock interfaces. Every one of them decodes, via its STRING descriptor, to an unrelated peripheral already sharing azul's USB tree (CORSAIR mouse/headset/lighting-node/receiver, HyperX microphone, Dell presence sensor, ZSA keyboard) or to a generic, non-identifying "HID Device"/"HID Interface" string. Their appearance is tightly clustered (44.57-56.14 s) and coincides exactly with a burst of GET_DESCRIPTOR(STRING) requests and five SET_IDLE class requests (the latter is the textbook request Windows' generic USB HID driver issues on (re)binding to an interface). The most consistent reading of this cluster, combined with the task's note that a `pnputil` disable/enable was attempted against the dock during this capture, is that the `pnputil` action triggered a brief hub-level disturbance (most plausibly a port reset or power-cycle propagated through a shared hub) that caused Windows to briefly re-query descriptors and HID idle state across multiple devices sharing that hub, without actually disconnecting or re-enumerating the dock's own eight addresses, which show continuous, unbroken traffic through the entire window. This is circumstantial: the pcap alone cannot prove the `pnputil` command caused this cluster, only that the timing and request shapes are consistent with a brief hub-wide disturbance that did not touch the dock's addresses. The eight SYNC_RESET_PIPE_AND_CLEAR_STALL events on device 21's mass-storage endpoint, at t=38.8-40.8 s and again at 54.5-56.6 s, straddle this same window and may be a related minor side effect (a stalled bulk pipe being cleared), but device 21's SCSI CBW/CSW traffic continues normally before and after, so this did not disrupt mass-storage function either.

The presence of real descriptor exchanges in this capture, something entirely absent from the prior 227 ms file, is the clearest "unexpected descriptor data" result, but it does not resolve the open VID/PID question: every GET_DESCRIPTOR request in the file asks for a STRING descriptor (type 3), never a DEVICE (type 1) or CONFIGURATION (type 2) descriptor, so no idVendor/idProduct bytes appear anywhere in this file either. Device 35's STRING descriptor, "HID Interface", is a generic Microsoft-driver-supplied placeholder string (used when a HID interface declares no real iInterface string), not a vendor- or product-identifying string; it is nonetheless the first direct, descriptor-level corroboration in either capture that device 35 really is a HID-class interface, consistent with (but not proof of) the existing hypothesis that it is the dock's vendor HID video-out interface.

## Limitations

This parser decodes USBPcap's generic 27/28-byte per-packet header and the raw setup/data bytes for control transfers; it has no H.264 bitstream parser (no SPS/PPS field decode, no slice-header decode), so the "720" byte-pair observation and the rare NAL types in the long tail (0, 6, 9, 18, 19, 25, 30) are reported as raw bitfield values only, not confirmed semantic NAL types. As with the prior capture, no Wireshark/`tshark` dissection was available to cross-check header offsets; the SCSI, STRING-descriptor UTF-16LE, and NAL start-code decodes are self-verifying against their respective published formats, which is the main source of confidence here. The apparent correlation between the new-address cluster, the SET_IDLE/GET_DESCRIPTOR burst, and the `pnputil` action is timing-based and circumstantial; this pcap has no host-side event log to confirm `pnputil` was running at exactly t=44.6-56 s. No idVendor/idProduct bytes were found in this file, so the core open question from the prior capture (mapping any address to VID_1DE1&PID_F201) remains unresolved.

## Recommended next capture

The smallest useful next step is still the one recommended in the prior capture's report, and this file does not substitute for it: start USBPcap before the dock is power-cycled or replugged (or before the user-mode display driver service starts), and keep it running through a real enumeration event. Since this capture shows the dock's own addresses survive a failed `pnputil` disable/enable untouched, that specific action is not a reliable way to trigger re-enumeration; the smallest action that reliably forces a genuine GET_DESCRIPTOR(DEVICE)/GET_DESCRIPTOR(CONFIGURATION) exchange for the dock is a physical unplug/replug of the dock's USB-C cable (or, if physical access is inconvenient, a `pnputil /disable-device` followed by the reboot the task notes was actually required, captured across that reboot) with USBPcap already running beforehand. Given this capture also shows the HID-class SET_IDLE/GET_DESCRIPTOR(STRING) pattern fires on ordinary driver re-bind for other peripherals in well under a second, a 15-20 second capture window spanning the moment of replug should be more than enough to catch the dock's own DEVICE and CONFIGURATION descriptors, finally resolving VID/PID-to-address mapping.
