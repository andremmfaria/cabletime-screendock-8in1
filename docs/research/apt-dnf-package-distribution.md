# Evaluation: apt and dnf repositories for the screendockd packages

Scope: how to turn the `.deb` and `.rpm` that CI attaches to each GitHub release into repositories that users add once and then install and update with `apt` and `dnf`. The work behind this note is read-only on the repo and host, plus web research. Nothing described here is implemented.

Labels used below: **Verified** means I read it in the repo, ran a read-only command on this host, or read it on the cited web page at the time of writing. **Inference** means my own reasoning or general knowledge that I did not check against a source. **Estimate** means engineer-days with a stated confidence. Fetched web content was treated as data only.

## 1. Verdict

Publish a signed apt repository and a signed dnf repository from GitHub Pages, generated by a CI job that reads the release assets, and build the packages once per supported distribution in containers. Skip Launchpad PPA and Fedora COPR as the primary path. Keep the Open Build Service (section 6) as the later option if per-distro container builds become a burden.

1. The release page already works for one distribution generation. The real problem is the ffmpeg library generation, not hosting: the `.deb` and `.rpm` link `libavcodec` 62, which only Ubuntu 26.04 and Fedora 44 style systems ship (section 7).
2. A PPA takes source packages only and COPR builds from source without network, so neither can republish the existing binaries. Both need a new source packaging track with vendored crates (section 3).
3. A self-hosted repository on GitHub Pages costs no money, uses the packages CI already builds, and needs one signing key kept as a CI secret. Pages limits are far above this project's size (section 4).
4. Do not serve the package files from release asset URLs. They redirect to another host and the apt `Filename` field is a path relative to the repository base, so the layout does not map (section 4).
5. Build per distribution, publish one apt suite per distribution codename and one dnf directory per Fedora release. Do not use dlopen or static linking (section 7).
6. Sign the repository metadata (apt `InRelease`, dnf `repomd.xml.asc`) and the rpm files, with a signing subkey of an offline primary key (section 8).
7. Likely cost: about 13 engineer-days for the full multi-distro result, 5 of them for a first repository that serves the single distribution the current packages already match (section 9).
8. Main risks: the codebase may not compile against ffmpeg 6.1 or 7.1, and a re-tagged release at the same version rebuilds files whose checksums change, which breaks clients that cached the old metadata (section 9).

## 3. Launchpad PPA and Fedora COPR

### Launchpad PPA

- Verified: the Launchpad PPA page lists uploadable artefacts as "Source packages only; pre-built binary uploads are rejected" and the package format as `.deb` only (https://help.launchpad.net/Packaging/PPA). A second source states the same reason, that Launchpad builds the binaries itself (https://askubuntu.com/questions/189529/can-i-upload-binary-packages-to-a-launchpad-ppa, search snippet).
- Verified: the upload uses `dput ppa:<id>/<name> <source.changes>` (https://documentation.ubuntu.com/launchpad/user/how-to/packaging/ppa-package-upload), and the email address and GPG key used for the upload must match the Launchpad account (https://documentation.ubuntu.com/launchpad/user/reference/packaging/ppas/building-a-source-package, search snippet).
- Verified: a Rust project is packaged by combining `cargo vendor` with `cargo build --frozen` and a `.cargo/config` that points crates.io at the `vendor` directory, so the build touches no network (https://blog.zhimingwang.org/packaging-rust-project-for-ubuntu-ppa). The same page notes the vendor tree can be checked into `debian/` or packed and expanded during the build.
- Inference: Launchpad builders have no network during the build, so offline vendored crates are required. A source package needs `debian/control` with build dependencies (`cargo`, `rustc`, `clang`, `pkg-config`, `libavcodec-dev`, `libavformat-dev`, `libavutil-dev`, `libswscale-dev`, `libavdevice-dev`, `libx264-dev`, `libpipewire-0.3-dev`, `libspa-0.2-dev`), `debian/rules` calling dh with the vendored build, `debian/changelog`, `debian/copyright`, a vendored tarball and one signed upload per Ubuntu series (for example a `~noble1` and a `~resolute1` version suffix). The Rust toolchain in the series must be new enough for the crate; that is unchecked. The system terminal files, maintainer scripts and udev rules would be re-expressed as `debian/*.install`, `debian/*.postinst` and `dh_installsystemd` inputs.
- Inference: effort is a new packaging track, 6 days low, 10 likely, 20 high, low confidence, and it only reaches Ubuntu users.

### Fedora COPR

- Verified: COPR takes a spec file or SRPM, uploaded, by URL, from SCM or through a custom source script (https://docs.copr.fedorainfracloud.org/user_documentation.html and https://docs.copr.fedorainfracloud.org/custom_source_method.html). The SRPM generation step may use the network and clone repositories; the RPM build itself does not.
- Verified (community answer, medium confidence): COPR does not allow network access during builds, so a Rust project needs either dependencies as RPM packages generated with `rust2rpm`, or a `cargo vendor` tarball supplied as an extra source (https://discussion.fedoraproject.org/t/how-do-i-use-copr-with-rust-and-dependencies/91676). The same thread says COPR deletes repositories when a release goes end of life.
- Inference: COPR cannot take a prebuilt `.rpm` as a package. A spec can repackage a binary tarball in `%install`, but that skips the build isolation COPR is designed around and I did not find a statement that it is allowed; treat it as unavailable. A normal COPR build needs a spec with the vendored source, `BuildRequires` for ffmpeg-devel and PipeWire-devel, and the RPM Fusion ffmpeg development packages (`ffmpeg-devel`) because the build uses `libx264` through ffmpeg. Whether a COPR chroot can enable RPM Fusion was not checked.
- Inference: effort 4 days low, 7 likely, 12 high, low confidence. It reaches only Fedora (and compatible) users and gives COPR's own hosting and signing.

## 4. Self-hosted apt repository

### Format and signing

- Verified: the Debian repository format has a mandatory `Filename` field in `Packages` that is the package path relative to the repository base directory (https://wiki.debian.org/DebianRepository/Format, search snippet). A flat repository puts the indices directly in the archive root without the `dists` tree (https://help.sonatype.com/en/apt-repositories.html, https://safeguard.sh/resources/blog/flat-apt-repository-or-dists-layout-for-a-small-vendor).
- Verified: apt `sources.list(5)` supports the deb822 style with `Types`, `URIs`, `Suites`, `Components` and `Signed-By` fields (https://manpages.debian.org/unstable/apt/sources.list.5.en.html). Debian's guidance for third party repositories is that repositories must be signed with an OpenPGP key and the key is referenced with `Signed-By` (https://wiki.debian.org/DebianRepository/UseThirdParty, search snippets). `/etc/apt/keyrings` is the conventional directory for admin-installed keys (Inference, widely used; the page itself could not be fetched here).
- Inference: the signed files are `dists/<suite>/InRelease` (clear-signed) and `dists/<suite>/Release.gpg` (detached). Modern apt needs only `InRelease`, and shipping both costs nothing.

### Tool comparison

| Tool | What it is | Fit here |
|---|---|---|
| `apt-ftparchive` | Part of the `apt-utils` package. Generates `Packages` and `Release` from a directory tree. Signing is a separate `gpg` step | Fewest moving parts, stateless, fits "rebuild everything from release assets on each run" (Inference) |
| `reprepro` | Maintains a pool and `dists` from a `conf/distributions` file, signs with `SignWith`, keeps a database of old versions (https://manpages.ubuntu.com/manpages/noble/man1/reprepro.1.html) | Good when several suites and a kept history are needed; its `db/` state must be persisted or rebuilt |
| `aptly` | Repository and snapshot manager that publishes to a filesystem or S3 endpoint (https://manpages.debian.org/unstable/aptly/aptly.1.en.html) | More than needed for one package |
| `deb-s3` style | Uploads a package and updates the manifest in S3 (https://github.com/renderinc/deb-s3) | Needs object storage; not needed with Pages |
| Flat repository | Indices next to the `.deb` files, `Suites: ./` | Valid, but one suite only, so it does not solve per-distro builds |

Recommendation: `reprepro` or `apt-ftparchive`. `apt-ftparchive` is enough for a handful of suites and has no database; `reprepro` is easier to extend. Both are Inference-level judgements.

### Hosting on GitHub Pages

- Verified: Pages sites may be no larger than 1 GB, have a soft bandwidth limit of 100 GB per month, deployments time out after 10 minutes, and the soft limit of 10 builds per hour does not apply when the site is built and published with a custom GitHub Actions workflow (https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits). The source repository has a recommended limit of 1 GB on the same page. Pages is not allowed for sites primarily for commercial transactions or SaaS.
- Verified: a release allows up to 1000 assets, each under 2 GiB, with no limit on total release size or bandwidth (https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases).
- Inference: at 2 to 2.5 MB per package, 3 suites plus 2 Fedora releases and 10 retained versions come to about 100 MB, well under 1 GB. 100 GB of monthly bandwidth is about 40000 package downloads, plenty for this project. Publish with the Actions Pages deployment (`actions/upload-pages-artifact` and `actions/deploy-pages`) instead of a `gh-pages` branch, because a branch stores every binary revision in git history and bloats the repository. A blog comparing the two approaches exists (https://blog.linux-ng.de/2026/10/21/apt-repository-github-pages-branch-or-github-actions) but could not be fetched here.
- Inference: the site is stateless. Each run downloads the release assets of the retained versions with `gh release download`, rebuilds `pool/` and the indices, signs and deploys. The release remains the source of truth and Pages is a derived artefact.
- Verified: ready-made Actions exist for this (for example https://github.com/ziptie-soft/pkg-pages, a GitHub Action that signs `.deb` and `.rpm` and publishes APT and RPM repositories to Pages, and https://github.com/marketplace/actions/create-apt-repository). I did not audit them. Writing the 40 lines of shell directly keeps the supply chain small and is preferable for a signing job (Inference).

### Serving package files from release assets

- Verified: release asset downloads redirect to a different storage host; community reports show `release-assets.githubusercontent.com` and `objects.githubusercontent.com` backends (https://github.com/orgs/community/discussions/165767) and the REST docs say a browser should follow the `browser_download_url` (https://docs.github.com/rest/releases/assets).
- Inference: this is fragile for apt for three reasons. The `Filename` field is relative to the repository base, but release asset URLs are flat per tag (`.../releases/download/<tag>/<file>`), so a normal `pool/main/s/screendockd/` layout cannot be served by them. The redirect target URLs are signed and temporary, and any tool that does not follow redirects, or a proxy that caches by URL, breaks. A re-tag at the same version replaces the asset behind the same URL, so the checksum in `Packages` stops matching. A flat repository with `URIs: https://github.com/<owner>/<repo>/releases/latest/download/` and `Suites: ./` could work in principle with the indices attached as release assets, but I did not test it and it supports one suite only.
- For dnf, Verified: `createrepo_c` has `--baseurl` ("Optional base URL location for all files", https://man.archlinux.org/man/extra/createrepo_c/createrepo_c.8.en), so metadata can point package locations at another host. Inference: it has the same redirect and replaced-asset weaknesses. Serving the files from Pages is simpler.

## 5. Self-hosted dnf repository

- Verified: `createrepo_c` generates `repodata/`, compresses with a selectable type including zstd, and uses sha256 checksums by default (https://man.archlinux.org/man/extra/createrepo_c/createrepo_c.8.en). Signing the metadata is a detached signature `gpg --detach-sign --armor repodata/repomd.xml` that produces `repodata/repomd.xml.asc` (https://blog.packagecloud.io/how-to-gpg-sign-and-verify-rpm-packages-and-yum-repositories).
- Verified: dnf has two independent checks. `gpgcheck` verifies package signatures and `repo_gpgcheck` verifies the repository metadata signature, and `repo_gpgcheck` defaults to false; the keys for the two checks are stored separately (https://dnf.readthedocs.io/en/latest/conf_ref.html). A forum thread notes that Fedora and RPM Fusion do not sign `repomd.xml`, so repo_gpgcheck is off for them by design (https://discussion.fedoraproject.org/t/why-does-dnf-give-gpg-signature-verification-errors-for-repos-with-repo-gpgcheck-1/147201). A dnf5 issue reports the key import prompt repeating for `repo_gpgcheck` (https://github.com/rpm-software-management/dnf5/issues/2923), so the first-use experience needs a test.
- Inference: sign each `.rpm` with `rpmsign --addsign` (the `rpm` package is already installed in `package.yml`) so `gpgcheck=1` works, and sign `repomd.xml` for `repo_gpgcheck=1`. Host `repodata/` and the rpm files on Pages under one directory per Fedora release, with a `$releasever` or fixed path in the `.repo` file. `cargo-generate-rpm` does not sign; I did not check whether it can.

## 7. Multi-distro problem

Verified facts:

- The v1.6.0 packages link `libavcodec.so.62`, `libavdevice.so.62`, `libavutil.so.60` and `libswscale.so.9` (section 2).
- Ubuntu 26.04 ships ffmpeg 8.0.1 (https://ubuntu.pkgs.org/26.04/ubuntu-universe-amd64/libavcodec62_8.0.1-3ubuntu2_amd64.deb.html). Ubuntu 24.04 ships ffmpeg 6.1.1 and Debian 13 ships 7.1.x (https://www.ucartz.com/clients/knowledgebase/2416/How-to-Install-FFmpeg-on-Linux-Ubuntu-Debian-AlmaLinux.html, https://packages.debian.org/trixie/ffmpeg shows `libavcodec61`).
- Fedora 43 has ffmpeg 7.1.2 and Fedora 44 has an 8.x ffmpeg (https://www.facebook.com/groups/Fedora.linux/posts/10172945618665249, https://www.ucartz.com/clients/knowledgebase/1416/How-to-Install-FFmpeg-on-Fedora-ffmpeg-free-or-Full-FFmpeg-from-RPM-Fusion.html). These are secondary sources, medium confidence.
- Fedora's own repositories carry `ffmpeg-free` and `libavcodec-free`, with limited codecs; RPM Fusion carries the full `ffmpeg` and `ffmpeg-libs` with `libx264`, and `libavcodec-freeworld` complements the free libraries (https://discussion.fedoraproject.org/t/dependency-hell-with-libaavcodec-free/191635, https://rpmfusion.org/CommonBugs). The package name `ffmpeg-libs` that the rpm requires is the RPM Fusion name (Inference from these pages).

Consequences:

- The current deb installs only where `libavcodec62` and related packages exist: Ubuntu 26.04 and anything with ffmpeg 8. The current rpm installs only where `libavcodec.so.62` is provided, so Fedora 44 with RPM Fusion, and not Fedora 43 (Inference from the version data).
- Fedora users must enable RPM Fusion Free before `dnf install screendockd` can resolve `ffmpeg-libs`, because the encoder needs `libx264`. The dnf repository cannot enable RPM Fusion for them; the install snippet must say so. Whether `ffmpeg-free` plus `libavcodec-freeworld` would also satisfy the soname requirement but not the package name `ffmpeg-libs` is unchecked.

Options:

| Option | Assessment |
|---|---|
| Build per distro in containers (`ubuntu:24.04`, `ubuntu:26.04`, `debian:13`, `fedora:43`, `fedora:44`) | Verified approach in principle: the binary and its soname dependencies come from the same distribution. Inference: it is the only option that keeps the current build and package metadata. Risk: the code must compile against ffmpeg 6.1, 7.1 and 8 through the `ffmpeg-next` bindings; unchecked |
| Make ffmpeg a runtime dlopen dependency | Inference: the libav structs and enums change across major versions, so a single binary talking to 6, 7 and 8 through hand-written bindings is unsafe, and `ffmpeg-next` has no dlopen mode that I found. High effort and a new bug class |
| Static link ffmpeg and x264 | Inference: libx264 is GPL, so statically combining it with an MIT binary makes the distributed binary GPL; this needs a licensing decision and a build of ffmpeg in CI. Larger packages and security updates no longer follow the distribution. Not recommended |
| Per-distro suites in one repository (`dists/<suite>`) | Required by the per-container approach for apt, because one suite cannot hold a different `screendockd` build per distribution. Use the codenames `noble`, `resolute`, `trixie` (Verified: `resolute` is this host's series, `noble` is Ubuntu 24.04's codename in https://manpages.ubuntu.com/manpages/noble/man1/reprepro.1.html, `trixie` is Debian 13's in the Debian pages above). For dnf use one directory per Fedora release |

Build in the oldest supported container of each family when the glibc symbol version matters. The v1.6.0 binary needs `GLIBC_2.34`, which all the listed targets provide (Inference from section 2).

## 8. GPG key handling

- Verified: a GitHub Action to import a key supports using a named subkey for signing (https://github.com/crazy-max/ghaction-import-gpg). A passphrase-protected key needs a loopback pinentry in non-interactive runs (Inference, common practice).
- Inference, recommended handling:
  - Generate a primary key with certify capability only, on an offline machine, with a long expiry (for example 3 years) and extend it before it expires. Add a signing subkey with a shorter expiry (for example 1 year). Create and store a revocation certificate offline.
  - Export only the secret subkey (`gpg --export-secret-subkeys`) and store it as the secret `REPO_GPG_PRIVATE_KEY`, with `REPO_GPG_PASSPHRASE` as a second secret. Keep both in a protected GitHub environment limited to the publish job so pull requests and other jobs cannot read them.
  - In the job, import the key into a throwaway `GNUPGHOME`, sign with `--pinentry-mode loopback --passphrase-file`, and delete the home afterwards.
  - Publish the public key at fixed paths on the repository site: `keyring/screendockd.gpg` (binary, for apt `Signed-By`) and `keyring/screendockd.asc` (armored, for dnf `gpgkey=`), and keep a copy in the git repository so users can compare it with the one on the site.
  - Rotation: add a new signing subkey before the old one expires and publish the updated public key. Clients that stored the old key file need to fetch the new one; the snippet should be re-runnable. Revocation: if the subkey leaks, revoke it with the primary key and publish the revoked public key; if the primary leaks, use the revocation certificate and announce a new key. Rotating the primary key means every user changes their stored key file.
  - Sign every rpm and the repository metadata with the same subkey. The deb files themselves need no signature, because apt verifies the signed `Release` and the hashes in `Packages`.

### CI job sketches

New workflow `.github/workflows/repo.yml`, called from `package.yml` after the release step with `workflow_call`, and runnable by `workflow_dispatch`. Permissions: `contents: read`, `pages: write`, `id-token: write`.

- `build-deb` matrix over `ubuntu:24.04`, `ubuntu:26.04`, `debian:13` containers: install build dependencies, `cargo build --release --features encode-ffmpeg,capture-wayland`, `cargo deb --no-build --deb-version <version>-1~<codename>`, run `deploy/check-packages.sh`, upload the artifact. Needs no secret.
- `build-rpm` matrix over `fedora:43` and `fedora:44` containers with RPM Fusion Free enabled for the development packages: same build, `cargo generate-rpm`, check, upload.
- `publish` (environment `repo-signing`, needs the two secrets): download the artifacts, import the key into a temporary home, `rpmsign --addsign` the rpm files, `createrepo_c` and detach-sign each `repomd.xml`, `reprepro includedeb` (or `apt-ftparchive packages` and `release` plus `gpg --clearsign` and `--detach-sign`) for each suite, copy the public key, run `actions/upload-pages-artifact` and `actions/deploy-pages`.
- `verify` (no secrets): in fresh containers of each distribution, add the repository with the user snippet and run `apt install` or `dnf install`, then `screendockd --version`. This job is the go and no-go gate for the stage.
- Release asset upload keeps working as it does now, so the release page stays a fallback.

Secrets needed: `REPO_GPG_PRIVATE_KEY`, `REPO_GPG_PASSPHRASE`. Pages must be enabled with the "GitHub Actions" source in the repository settings.

### Go and no-go criteria

- Go for stage 1 when a fresh container of Ubuntu 26.04 and one of Fedora 44 can add the repository from the snippets and install, start `screendockd --version` and upgrade to a newer package, with signature checks on.
- Go for stage 2 for a distribution only when the code builds against its ffmpeg and `deploy/check-packages.sh` passes; otherwise drop that distribution. If two of the three extra targets fail on ffmpeg API differences, stop and consider OBS or a minimum supported ffmpeg policy instead.
- No-go on Pages if the site approaches 500 MB (halve retention) or the monthly bandwidth warning appears; move the files to Cloudsmith's open-source tier.
- No-go on automatic publishing until the same-version rebuild issue below is solved.

### Risks

1. Same-version rebuilds. `tag-release.yml` re-tags and rebuilds on every push at an unchanged version, and the asset bytes change. Clients that cached `Packages` or `repomd.xml` see hash mismatches while they update, and Debian policy expects a version to be immutable (Inference). Mitigation: publish the repository only when the `Cargo.toml` version changes, or add a package revision that increments per build.
2. ffmpeg API drift across 6.1, 7.1 and 8 may block older targets (Inference).
3. Key custody. A leaked signing subkey lets an attacker serve code that runs as root (the packages install a root `login` terminal and udev rules, Verified in `docs/install.md`). Use a protected environment, subkeys, short expiry and an offline primary.
4. RPM Fusion dependency. The dnf repository needs a third-party repository enabled first, and its ffmpeg may lag Fedora releases (Inference).
5. GitHub Pages terms and limits could change; the layout is a plain static tree that moves to any host.
6. Single maintainer: key expiry that is missed makes `apt update` fail for every user. Put the expiry date in the rotation runbook.
