# Linux driver feasibility — write-path proof of concept and remaining unknowns (2026-11-21)

## Headline result: writing to the device works, confirmed live

Every write attempt earlier this session (`HidD_SetOutputReport`, both Report ID 1 and Report ID 2, with both garbage and correctly-framed content) failed at the transport level (`ERROR_GEN_FAILURE`/31) even with the official app and service fully stopped. This left a real open question: does writing to this device actually work at all, via any mechanism?

Resolved this pass. The Ghidra analysis had already established that `USBDisplayService.exe` uses **hidapi** (a cross-platform library) for its one confirmed write (the MI_00 heartbeat). hidapi's `hid_write()` on Windows, when the target HID collection has a dedicated interrupt OUT endpoint, calls plain **`WriteFile`** directly on the device handle — not `HidD_SetOutputReport`, which instead issues a USB HID class-specific "Set Report" control request. These are genuinely different wire-level mechanisms. Retested with plain `WriteFile`, correct Report ID byte (`2` for MI_01), and a **real captured keyframe bundle** (extracted verbatim from the cold-start capture: one HID message, offset 0 = SPS NAL type 7, offset 26 = PPS NAL type 8, offset 35 = SEI NAL type 6, offset 719 = IDR slice NAL type 5, total message length 3577 bytes, fits in one 4096-byte HID report) — the write succeeded (`WRITEFILE_OK bytes_written=4096`), and the user confirmed the dock's screen visibly blinked/reacted at the moment of the write.

This is the decisive proof the earlier write attempts couldn't provide: the device is genuinely writable, the exact framing already reverse-engineered (report ID, 16-byte header, chunking) is correct enough to produce a real firmware-level reaction, and the correct host-side mechanism is a direct interrupt-OUT `WriteFile`/`hid_write()`-style call, not the Windows-specific `HidD_SetOutputReport` control-request path. On Linux, the equivalent and natural mechanism is `write()` on `/dev/hidrawN` (or `hidapi`'s own `hid_write()`, which does the same thing cross-platform) — no custom kernel module is needed, since this is a standard vendor-defined HID interface that `hid-generic` already binds.

## New protocol clarification from this test: keyframe bundling

Inspecting the real captured message used in this test confirmed that a single HID message/chunk-sequence can carry **multiple concatenated NAL units**, not strictly one NAL per message: a keyframe message bundles SPS + PPS + SEI + IDR slice together (in that order, each with its own Annex-B start code) as one logical unit. Regular inter-frames are sent as single-NAL (type 1) messages, per the much larger sample set analyzed earlier this session. A Linux encoder pipeline should replicate this bundling for keyframes rather than sending SPS/PPS/IDR as three separate HID messages.

## What this means for a Linux driver

Scope correction worth restating: this is not a kernel driver project. `MI_00`/`MI_01` are vendor-defined (`UsagePage=FFFF`) HID collections, which Linux's generic `hid-generic` driver binds automatically, exposing `/dev/hidrawN` with no vendor kernel module needed. The actual deliverable is a **userspace daemon**, directly analogous to `USBDisplayService.exe`: capture the screen, encode H.264, chunk and write it to the MI_01 hidraw node, while a second thread/loop sends the MI_00 JSON-RPC heartbeat on a steady cadence to keep the dock out of its "Connecting Signal..." overlay state.

Confirmed building blocks, high confidence:
- MI_00 heartbeat: exact JSON-RPC format and cadence, Report ID 1.
- MI_01 video: exact framing (Report ID 2, 16-byte header on first chunk, raw continuation chunks, 4096-byte HID reports), confirmed via code and now confirmed writable via a real device reaction.
- Target encode parameters: H.264 Constrained Baseline, 1280×720, no B-frames — standard, achievable with `libx264`/`ffmpeg` on Linux.
- Keyframe bundling (SPS+PPS+SEI+IDR as one message) vs. single-NAL inter-frames.
- The write mechanism: direct `WriteFile`/`hid_write()`/`write()` to the device's interrupt OUT path, not the OS's "Set Output Report" class-request abstraction.

## Remaining unknowns before committing to a full driver

- **Sustained multi-frame streaming has not been tested.** This pass proved exactly one isolated frame write causes a visible reaction. Not yet tested: writing a continuous sequence of frames at a real frame rate (the live captures showed ~25fps, ~35 messages/sec average), and whether the dock renders a stable, continuously-updating picture rather than single blinks. This is the next concrete test to run before writing a real daemon.
- **Multi-chunk (>4080 byte) continuation writes are untested live.** This pass only wrote a single-chunk message (3577 bytes fit in one report). Real captures show messages up to ~256KB requiring many continuation chunks. The continuation chunk *format* is confirmed from passive capture (1-byte Report ID + raw payload, no header), but issuing a real multi-chunk *write* sequence (timing between successive `WriteFile` calls, whether there's a maximum inter-chunk delay before the device times out and discards a partial message) has not been attempted.
- **Whether sustained video requires the MI_00 heartbeat to be running concurrently.** Strong circumstantial evidence from earlier this session (killing `USBDisplayService` dropped the dock to "Connecting Signal..." even though, per this session's later finding, the video-shaped traffic on dev24 never actually stopped) suggests the heartbeat gates a UI overlay independent of the video feed — but this was never isolated as a clean two-variable test (video only vs. heartbeat only vs. both). Worth confirming directly: does video alone (no heartbeat) show on screen, or does it need the heartbeat running too?
- ~~Field A/B's exact numeric origin.~~ **Resolved empirically — no longer an open item.** A live multi-resolution/orientation test (cycling through every resolution Windows offered for the dock's virtual display, plus landscape/portrait rotation, across two capture sessions totaling ~490s and 9 distinct combinations) established a clean, zero-exception formula: **field A is always `0`; field B = target display width in pixels × 256** (post-rotation width, if rotated). Cross-validated against directly-decoded H.264 SPS width in every case. Height is carried purely by the standard H.264 SPS NAL itself (ordinary macroblock padding/cropping) — field A/B never encode height at all, confirmed directly by one segment where height varied (960→800→720) while width (and therefore field B) stayed constant. The underlying static-analysis code path that produces these values was never fully explained at the instruction level (traced to a contradiction — see `full-protocol-spec-2026-11-21.md`), but that no longer matters for implementation purposes: the empirical formula is reproducible and sufficient on its own.

  **For a Linux resolution-picker:** fully unblocked. Set `fieldA = 0`; compute `fieldB = target_width * 256` for whichever width is actually being encoded; let the H.264 encoder handle height and coded-size padding normally. No further unknowns here — this was the one open item standing between "driver works at native resolution" and "driver supports a real resolution-switching feature," and it's now closed.
- **No resolution negotiation path exists** (confirmed via Ghidra — resolution is fixed OS-side via the IddCx virtual-display mode list, not queried from the dock over HID): the dock never tells the host what resolutions it supports, the host just picks one and tells the dock via field B (see above). A Linux daemon is free to support multiple resolutions, as long as it computes field B correctly for whatever width it's actually encoding — it should not attempt to query the device for supported modes, since no such query mechanism exists.
- **Whether anything else needs acknowledging.** MI_01 produces no input reports when read (confirmed earlier this session), consistent with a pure one-way, fire-and-forget output channel with no ACK/handshake — but this was inferred from a 25-second read timeout, not exhaustively proven over a long window.
- **Touch/digitizer input (the `Col02` collection on both MI_00 and MI_01, UsagePage `000D`/Digitizer) was not explored at all.** Not required for basic display-only use, but relevant if two-way interaction (dock-side touch events, if this SKU ever has them, or synthesized mouse input mirroring the Mac driver's `AMHIDEventFakeMouseProcessor`) is ever wanted on Linux.
- **The dock's SD/TF card reader port identity (Terminus hub port 1) remains inferred, not directly confirmed** — unrelated to the driver itself, listed here only because it's the last open item from the broader protocol-mapping work.

## Recommended next step

Before writing any real encoder/capture pipeline: run a short sustained test (a few seconds, real frame rate) writing a real short H.264 GOP (one keyframe bundle + a handful of P-frames) to MI_01 via the confirmed `WriteFile` mechanism, with the MI_00 heartbeat running concurrently, and visually confirm a stable, correctly-rendered moving picture — not just a single blink. That one test would retire the two biggest remaining unknowns (sustained streaming, heartbeat-dependency) at once and would be the real go/no-go signal for committing to a full Linux daemon.

## Follow-up: sustained streaming test performed, and the multi-chunk timing sensitivity confirmed

Ran the recommended test: replayed a real 5-second window of captured bytes (298 records: 9 MI_00 heartbeats + 289 MI_01 video messages, in original chronological order, via sequential `WriteFile` calls with `Thread.Sleep` matching the original inter-record delays) against the live device with the official app/service still running normally. All 298 writes succeeded at the OS level (0 failures). Visually, this **partially** retires unknowns 1 and 3: sustained multi-second writing via the confirmed mechanism works without errors and the official app wasn't disrupted by concurrent writes, but the rendered result was only a small patch of correct-looking pixels in the top-left corner, not a stable full picture — matching, almost exactly, the partial-decode pattern an independent `ffmpeg` software decode of the same reassembled byte stream had already shown earlier in this investigation (also correct only in the first few macroblocks). Two independent decoders (software `ffmpeg` and the dock's real hardware decoder) failing in the same specific way is strong evidence the defect is in this project's reassembly/replay fidelity, not in the underlying protocol understanding.

**Root cause, confirmed by direct measurement:** real captured multi-chunk messages have continuation chunks arriving sub-millisecond apart (0.76–0.91ms average gap, measured directly from the pcap) — essentially back-to-back at the USB interrupt endpoint's natural polling rate. The original 5-second replay used an explicit `Thread.Sleep(delayMs)` per record with integer-millisecond-rounded delays, plus per-iteration array-copy and delay-decoding overhead in the replay loop — on top of a measured raw `WriteFile` latency of ~0.77ms/call (close to, but not identical to, the original cadence). Retested with a tighter, targeted replay: one real keyframe bundle (3577 bytes, 1 chunk) + the very next real 17-chunk message (67,666 bytes) from the capture, written back-to-back via `WriteFile` with **zero explicit delay at all** (letting the synchronous write call's own natural pacing be the only timing) — 18 chunks completed in 13.93ms total (~0.77ms/chunk), closely matching the original capture's ~12.2ms for the same message. This produced a visibly larger correctly-decoded region — a full strip across the top of the screen, rather than just a small corner patch — confirming the mechanism is genuinely timing-sensitive (a structural reassembly bug would not have improved when only the timing changed) and that getting closer to the original cadence produces a proportionally more complete decode.

**Assessment for a real Linux daemon:** this is very unlikely to be a blocking issue in practice. The ~0.77ms/chunk figure observed here is close to the physical floor imposed by the interrupt endpoint's own USB polling interval under a synchronous write call — not something further software tuning inside an interpreted scripting harness (PowerShell + .NET, used for all of this session's live tests) can meaningfully improve. A real implementation would be a compiled native program using `hidapi` or raw `hidraw` writes directly (exactly the shape the eventual Linux daemon needs anyway, not a prototyping script), which removes the PowerShell/.NET interpreter and GC overhead layered on top of the raw write call in these tests and should get materially closer to — or at — the original cadence by construction, rather than needing a deliberate fix. Treat this as **resolved in principle** (the mechanism works and is timing-sensitive in a well-understood, physically-plausible way) rather than an open protocol question; the remaining gap is a prototyping-harness artifact, not something to design around.
