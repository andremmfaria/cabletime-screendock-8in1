# Windows USBPcap capture analysis, azul root-hub capture, 2026-11-21

Source file: `re/captures/usbcap-azul-root1-2026-11-21.pcap`. Parsed with a hand-rolled Python parser against the USBPcap global and per-packet header layout (no `tshark`/`capinfos`/`editcap`/Scapy/dpkt available on this host, so all facts below come from a manual struct-level decode of the raw bytes, cross-checked twice with independent scripts; parser scripts are kept under the scratch cache, not in this repo, per the read-only access rule for this task).

## Result

The capture is a 227 ms snapshot of USB bus 1 on azul containing 493 packets across eight distinct device addresses (16, 21, 23, 24, 26, 29, 30, 35). It contains no USB descriptor exchange (no `GET_DESCRIPTOR`, no `SET_CONFIGURATION`) for any of those addresses, so nothing in this file lets a parser map any device address to a VID/PID. There is therefore no demonstrated transaction that can be attributed to CABLETIME ScreenDock VID_1DE1&PID_F201 from this pcap alone; address-to-identity mapping is absent from the capture, not merely unparsed.

Despite that, the capture does contain a genuine host-to-device (OUT) HID payload carrying H.264 Annex-B elementary-stream bytes: ten interrupt-OUT packets on device address 35, endpoint 2, 4096 bytes each, each opening with a constant single byte (0x02) followed by a 3-byte Annex-B start code, a NAL header decoding to type 7 (SPS), a second start code, and a NAL header decoding to type 1 (non-IDR slice), with the remainder of the slice NAL running to roughly byte 343 and the rest of the 4096-byte report zero-padded. This matches, byte-for-byte in structure, the H.264/avc1 real-time codec already identified independently in `display-protocol-reverse-engineering.md` via static analysis of the Mac driver (VideoToolbox `avc1` setup). It is the strongest ground-truth evidence collected so far for that hypothesis, but it cannot be tied to the dock's VID/PID inside this file.

The capture also contains exactly one control-transfer pair (device address 23): a vendor-defined, device-to-host control request (`bmRequestType=0xC0`, `bRequest=0x05`, `wValue=0xE908`, `wIndex=0x0103`, `wLength=4`) answered with a 4-byte response `84 00 FF FF`. This is the only control-transfer/handshake-shaped exchange anywhere in the capture. It cannot be confirmed as the dock's handshake: device address 23 does not otherwise appear in the capture, so there is no corroborating bulk/interrupt traffic on that address to anchor it to a known interface, and no descriptor data links address 23 to VID_1DE1&PID_F201 either.

A separate address, device 21, carries a textbook SCSI CBW/CSW mass-storage transaction on bulk endpoints 1/2 (`USBC...` / `USBS...` signatures, an 18-byte data stage, a `REQUEST SENSE`-shaped CBWCB). This matches the shape of the dock's known mass-storage interface (MI_04) described in `usb-enumeration-check-2026-11-21.md`, but again only by shape, not by VID/PID, since this capture has no descriptor data for address 21 either.

## Evidence

Global pcap header, decoded from the first 24 bytes with `struct.unpack_from("<IHHiIII", data, 0)`: magic `0xa1b2c3d4`, version 2.4, snaplen 65535, `network` (linktype) 249, which is the registered `LINKTYPE_USBPCAP` value, confirming this is a genuine USBPcap-format capture and not a renamed/foreign file.

Per-packet record loop, decoded with `struct.unpack_from("<IIII", data, offset)` per 16-byte pcap record header followed by `incl_len` bytes of USBPcap packet data: 493 records parsed cleanly to end-of-file with no truncation; first record timestamp `1795264443.652912`, last `1795264443.880337`, giving a capture duration of 0.227425 s.

USBPcap per-packet header fields (base 27-byte generic header: `headerLen` u16 @0, `irpId` u64 @2, `status` u32 @10, `function` u16 @14, `info` u8 @16, `bus` u16 @17, `device` u16 @19, `endpoint` u8 @21, `transfer` u8 @22, `dataLength` u32 @23; control transfers that include a captured setup stage extend `headerLen` and append the 8-byte USB setup packet right after byte 27) decoded for every record:

Transfer-type counts: INTERRUPT 435, ISOCHRONOUS 46, BULK 10, CONTROL 2. Direction counts: OUT 247, IN 246. Distinct (bus, device) pairs: `(1,16) (1,21) (1,23) (1,24) (1,26) (1,29) (1,30) (1,35)`. URB function codes seen: `0x0009` (×445, `URB_FUNCTION_BULK_OR_INTERRUPT_TRANSFER`), `0x000a` (×46, `URB_FUNCTION_ISOCH_TRANSFER`), `0x0008` (×2, `URB_FUNCTION_CONTROL_TRANSFER`).

Per-(device, endpoint, transfer-type, direction) breakdown with payload-length histograms (payload = bytes after `headerLen`): device 24, ep1, interrupt, is by far the busiest combination (183 IN frames: 92×16-byte + 91×0-byte; 184 OUT frames: 92×64-byte + 92×0-byte), 74% of all frames in the capture. Device 35, ep2, interrupt-OUT: 10 frames of 4096 bytes (plus 10 corresponding 0-byte completion records). Device 30, ep3, isochronous-OUT: 23 frames of 2880 bytes, byte content all `0x00` (silence) in both sampled frames. Device 21, ep1/ep2, bulk: CBW `55534243 a037d758 12000000 80 00 0c 03000000120000000000000000000000`, CSW `55534253 a037d758 00000000 00`, matching data stage 18 bytes `70 00 02 00 00 00 00 0a 00 00 00 00 3a 00 00 00 00 00`. Device 16, ep4, interrupt, bidirectional 64-byte frames with a slowly-incrementing byte pattern (`08 06 00 24 00 00 00 ...`) unrelated in shape to video or mass storage. Device 29, ep1, interrupt-OUT only, 64-byte frames of repeating 2-byte colour-like tuples (`ff0d7a ff6d8b ff6d8b ...`), no IN traffic captured on that address. Device 26, ep1/ep2 interrupt, same packet shapes as device 24 but far fewer frames (6 each), suggesting the same interface class re-appearing at a different address, not a different kind of traffic.

Control-transfer frames (full USBPcap-header hex): frame 395, device 23, `headerLen=28`, setup-adjacent payload `c0 05 08 e9 03 01 04 00` (decoded as `bmRequestType=0xC0, bRequest=0x05, wValue=0xE908, wIndex=0x0103, wLength=0x0004`); frame 396, device 23, response payload `84 00 FF FF` (4 bytes, matching the requested `wLength`).

H.264 Annex-B scan (manual start-code finder, scanning every payload for the 3-byte sequence `00 00 01` and decoding the following byte as a NAL header): device 35's ten 4096-byte OUT payloads are byte-for-byte identical in structure across all ten occurrences (frames 0, 53, 107, 140, 182, 266, 270, 354, 462, 469): byte 0 = `0x02` constant; start code at byte offset 1, NAL header `0x47` (`forbidden_zero_bit=0, nal_ref_idc=2, nal_unit_type=7` = SPS); start code at byte offset 17, NAL header `0x41` (`nal_ref_idc=2, nal_unit_type=1` = non-IDR coded slice); real (non-zero-padding) payload runs to approximately byte 343 in every occurrence, with the remaining ~3750 bytes zero-padded to fill the 4096-byte report. The slice-NAL bytes differ slightly frame to frame (e.g. frame 0 vs frame 53 differ at several byte positions within the slice payload) rather than being bit-identical, consistent with successive compressed frames of largely static/idle screen content rather than one frame being replayed. No start-code/NAL-header pattern was found in any other device's non-zero payload except one coincidental single-byte match in device 16's traffic (`...00 01 2f...`, NAL type 15, an unassigned/rarely-used type, inside an otherwise non-video-shaped 64-byte packet); that is treated as a false positive, not a real NAL.

Device-descriptor byte-pattern scan (looking for `bLength=0x12, bDescriptorType=0x01` at the start of a standard 18-byte USB device descriptor) across every payload in the file: zero hits. No idVendor/idProduct bytes are recoverable from this capture by any method.

## Interpretation

This pcap was captured mid-session, after device enumeration had already completed; it is a slice of steady-state traffic, not an enumeration trace. That is consistent with `usb-enumeration-check-2026-11-21.md`'s note that USBPcap's kernel driver was not registered/running right after the last reboot and needed an explicit re-arm step; whoever captured this file evidently got the driver running and started capture sometime after the dock (and everything else on that root hub) was already up, so no descriptor traffic survived to anchor device identities.

The device-35 H.264 finding is the single most load-bearing result in this file. The byte layout (one leading constant byte, then Annex-B NAL units, SPS followed by a non-IDR slice, zero-padded to the HID report's full declared size) is exactly the shape predicted by the project's own prior Ghidra findings (VideoToolbox `avc1`, no B-frames, real-time, baseline-profile-shaped short SPS) and by the general theory in `display-protocol-reverse-engineering.md` that a packetizer chops NAL units into HID-sized chunks. The leading `0x02` byte is a plausible HID numbered-Report-ID prefix, which would align with that project's own "report 2" terminology, but this is circumstantial: Windows USB device addresses are session-local and not persistent, this capture carries no descriptor data for address 35, and the project's earlier hidraw experiment reasoned that endpoint 2/report 2 was device-to-host only (based on `ETIMEDOUT` on raw unprivileged OUT writes) — this capture shows real OUT traffic succeeding on that shape of endpoint under the official Windows driver stack, which either means that raw-write experiment's direction conclusion was wrong, or that device 35 here is a different interface than the one tested there. Either way, the discrepancy is itself useful: it suggests the real driver can write OUT video data on this endpoint, something a generic hidraw test apparently could not reproduce, hinting at some driver-side setup (configuration descriptor selection, feature negotiation, or simply correct chunk/report framing) that the raw test was missing.

The device-23 control transfer is the only candidate "handshake" pattern in the file, but it stands alone: no other traffic on address 23 appears before or after it in this short window, so there's no way to tell from this file whether it precedes streaming on another address, is unrelated enumeration housekeeping, or belongs to a different device on the bus entirely. It should not be reported as "the dock's handshake" without a capture that shows the same address immediately followed by HID/video traffic on the same device.

The device-21 SCSI CBW/CSW traffic matches the previously-documented "routine SCSI polling of the virtual CD-ROM" pattern from `display-protocol-reverse-engineering.md` section 3, reinforcing that this is background mass-storage housekeeping, not display protocol traffic, and not worth further analysis.

Devices 16, 26, and 29 show traffic shapes (small, mostly-static 64-byte interrupt frames; RGB-tuple-like repeating data) that do not resemble either H.264 payload or mass-storage signatures. Without descriptor data, these cannot be ruled in or out as dock interfaces (device 26 in particular repeats device 24's exact packet shapes at a much lower rate, which is consistent with either a second, idler instance of the same interface class, or coincidence).

## Limitations

This pcap alone cannot establish VID/PID for any address in it; that requires either a capture that includes enumeration (plugging the device in during capture, or a `SET_CONFIGURATION`/`GET_DESCRIPTOR` re-issued by the host) or a host-side log that timestamps `Get-PnpDevice` bus addresses against the capture window. No Wireshark/`tshark` dissection was available on this host, so all USBPcap field offsets above were decoded by hand against the published USBPcap header layout and should be spot-checked against Wireshark if it ever becomes available, though the SCSI CBW/CSW and H.264 NAL decodes are self-verifying (the magic signatures and NAL header bit-fields match their respective standards exactly, which is strong internal corroboration independent of the header-offset assumptions). The capture window is only 227 ms, too short to see more than a couple of video-report cycles or a full mass-storage command sequence, and far too short to see any true cold-start handshake if one exists outside this window.

## Recommended next capture

Capture again, but start USBPcap before the dock is connected to azul's HOST port (or, if that is impractical, before `USBDisplay.exe`/the Actions Micro driver's user-mode service is started), and keep it running through device enumeration and the first several seconds of active display. That one change would (a) capture the `GET_DESCRIPTOR` responses needed to map a device address to VID_1DE1&PID_F201 for the first time, directly answering the open identity question this file leaves unresolved, and (b) show whatever happens on that device's interfaces in the seconds immediately after enumeration, which is the most likely place for a real init/handshake sequence (as opposed to the device-23 control transfer here, which cannot be anchored to anything). No filter changes or longer duration are strictly required beyond "start before, not after" — a 10-to-15 second capture spanning cold connect through a few seconds of steady video would already contain everything this file is missing.
