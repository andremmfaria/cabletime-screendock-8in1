## Addendum: HID-level probing and write test (same session, later)

After the architecture re-think above, did direct OS-level HID probing (bypassing pcap entirely) using a small inline C# tool (PowerShell `Add-Type`, no installs needed — kept at `/home/andremmfaria/.hermes/cache/scratch/hid_enum2.ps1`, `hid_read_live.ps1`, `usb_speed_check2.ps1`, `hid_write_test2.ps1` on the local machine; copy to azul via scp before running). These are reusable for a future session.

### Confirmed facts
- The dock (`VID_1DE1&PID_F201`) has exactly two vendor-opaque (`UsagePage=FFFF`) HID top-level collections, one per interface: `MI_00&Col01` and `MI_01&Col01`, both declaring `InputReportByteLength=4096` and `OutputReportByteLength=4096` — matching the original capture's report size. Each interface also has a second collection (`Col02`, UsagePage `000D`=Digitizer, Usage `000E`=Finger, zero-length reports) — a touch/digitizer collection, consistent with the shared EZCast touch-capable codebase noted in `windows-mac-driver-correlation.md`, dormant on this non-touch SKU.
- `MI_00&Col01` read live via `HidD`/`ReadFile`: returns a real, consistent 4096-byte **JSON-RPC heartbeat** payload (`{"jsonrpc":"2.0","method":"heartbeat","params":{"session-id":"149...`). This is a status/control channel, not video. Its correct Report ID is `0x01` (confirmed from the live read's first byte).
- `MI_01&Col01` read live: no input report arrived in 25+ seconds (empty/blocking `ReadFile`). This interface is not actively pushing data to the host right now.
- USB hub topology fully mapped via `IOCTL_USB_GET_NODE_CONNECTION_INFORMATION_EX` (recursive hub enumeration script, `usb_speed_check2.ps1`): the dock sits on port 2 of hub `VID_1A40&PID_0801` (Terminus Technology — almost certainly the dock's own internal hub chip), running at **High Speed (USB 2.0, 480 Mbps)**. This is normal/expected for this device class, not a regression — ruled out as an explanation for the missing video traffic (USBPcap captures at the URB/IRP layer, above wire-level packetization, so bus speed doesn't change how many pcap records a given driver request shows as).
- Direct `HidD_SetOutputReport` write test (all-zero 4096-byte buffer): `MI_00` with ID=`0x01` and `MI_01` with ID=`0x02` both passed Windows' own parameter validation (other IDs returned `ERROR_INVALID_PARAMETER`/87) but failed with `ERROR_GEN_FAILURE`/31 at the transport level — consistent with the correct Report IDs being 1 and 2 respectively, but something (most likely `USB Display.exe` holding the pipe busy, possibly also the firmware rejecting a content-free all-zero payload) blocking the actual transfer. **No visible change on the dock's screen during either attempt** — confirmed by direct observation, so this was a safe negative result, not a destructive one.

### Where this leaves the investigation
We now have confirmed, reusable tooling (HID enumeration, live HID read, hub/port/speed mapping, HID write with correct Report IDs) that didn't exist before this session, and we've eliminated several false leads (RGB mouse, audio, presence sensor, link-speed regression, wrong Report ID). But the core question — which channel actually carries the live video frames the user can see on the dock's screen right now — remains unresolved. Three live USB captures covering confirmed-live video, totaling over 550 seconds, show no traffic shaped like real-time compressed video on any of the 8-12 devices present on the bus.

### Recommended next steps, in order of effort/risk
1. **Stop `USB Display.exe` cleanly first, then retry the `HidD_SetOutputReport` write test on both interfaces with the confirmed-correct Report IDs (1 and 2).** If the app's exclusive pipe hold is what's causing `ERROR_GEN_FAILURE`, removing it first should let the write actually reach the device, which would be immediately visible (garbage/noise on screen, or no change) regardless of content correctness.
2. **Capture again with USBPcap started BEFORE `USB Display.exe`/`USBDisplayService` starts**, so the capture includes the real startup/handshake sequence instead of only steady-state traffic — this is the single highest-value capture we have not actually taken this whole investigation (every capture so far started after the app was already running).
3. If neither of those finds it, consider that the video might not be delivered via `HidD`-level reports at all, but via a raw bulk/isochronous endpoint on one of the other interfaces (`MI_02`, `MI_04`) that hasn't been probed at the OS HID level (only `MI_00`/`MI_01` have HID collections; `MI_02` is audio-class, `MI_04` is mass-storage-class, but either could carry an additional vendor-defined endpoint not exposed through the HID API).
