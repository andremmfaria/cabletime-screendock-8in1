Session closing note, Windows USB capture phase, 2026-11-21.

Picked up this project after the prior session died mid-reboot of azul (192.168.10.166), the Windows PC used for the official CABLETIME ScreenDock driver. Verified azul had actually recovered from that reboot (ARP/ping reachable, wired on switch port 3) but its SSH service had not come back; RDP was available but excluded from use per the user's instruction, so the user manually re-enabled SSH on the box and work continued over that.

Confirmed the earlier session's pending state: the USBPcap kernel driver was RUNNING and correctly bound via the USB class UpperFilters registry value, and the official driver stack (USBDisplayService.exe, USB Display.exe) was live with the dock attached.

Captured USB traffic twice from the root hub carrying the dock (capture 1, 140 KB/227ms; capture 2, 39.9 MB/~71s) using USBPcapCMD. Both were mid-session snapshots, since no re-enumeration event occurred during either. Full analysis of capture 1 is in docs/research/windows-usb-capture-analysis-2026-11-21.md; capture 2's analysis, at far larger sample size, is in docs/research/windows-usb-capture-analysis-2-2026-11-21.md and corrects two of capture 1's provisional claims below.

The key result, confirmed across both captures and independent of any VID/PID anchor: device address 35, endpoint 2, interrupt-OUT carries real host-to-device H.264 Annex-B NAL data inside 4096-byte HID reports with a leading 0x02 byte and a structured ~17-byte header whose field at byte offset 14-15 holds a constant value of 720 (matching the dock's known frame height). Capture 1's small sample (10 reports) looked like every report was a full SPS+slice group; capture 2's 2,017-report sample shows that is not the typical case: about 78% of reports carry a single non-IDR slice NAL only, about 19% carry no NAL at all (idle/keepalive reports), and only 6 reports (0.3%) are full SPS+PPS+IDR keyframe groups. This still directly corroborates the project's independently-derived avc1/VideoToolbox hypothesis from the Mac driver's static analysis in docs/research/display-protocol-reverse-engineering.md, with real traffic from the official Windows driver rather than inference from binary analysis alone, now with a much clearer picture of the packetization pattern (periodic keyframe groups, routine slice updates, idle keepalives).

Capture 1 flagged a single vendor control transfer (device 23) as a possible handshake candidate but could not anchor it to anything else. Capture 2's full-length sample resolves this: that same request/response pair recurs 139 times at a steady ~0.51s cadence across the whole 71-second window, so it is periodic status polling, not a handshake, and should not be described as one going forward. Capture 2 also found real USB STRING descriptors (none were present in capture 1) for several devices on the shared hub, including a generic "HID Interface" string for device 35, but still no DEVICE or CONFIGURATION descriptor and no idVendor/idProduct bytes anywhere in either capture, so the VID/PID-to-address mapping question remains fully open.

Attempted two non-reboot paths to get a capture spanning actual device enumeration (needed to finally map a USB address to CABLETIME's VID_1DE1&PID_F201 and to see any real init handshake): pnputil disable/enable of the dock's composite device (failed outright, Windows requires a reboot for that device class), then a user-performed physical unplug/replug while a third capture ran. The physical replug did happen at the OS level (confirmed via a Microsoft-Windows-Kernel-PnP event log entry showing USB Display.exe vetoed the device's removal), but it crashed that capture (0-byte file) and left the dock's composite device missing its MI_00-MI_04 child interfaces until the user manually relaunched USB Display.exe from their desktop session, which did restore the full device tree. USBPcapCMD itself, however, stayed broken afterward: even trivial no-op invocations (-h) started exiting cleanly with no output, down from working normally earlier in the same session. That rules out a device- or driver-state problem and points to something exhausted in USBPcapCMD's own execution environment under repeated SSH-spawned invocations, which a reboot would clear but which the user chose not to force.

Decision, confirmed with the user: stop chasing the enumeration/descriptor capture. The H.264 finding from capture 1 stands as the deliverable for this phase. If a future session wants to resume the descriptor trace, the fix is straightforward: reboot azul once, confirm USBPcapCMD's -h/-d run cleanly first, then do one physical unplug/replug while a fresh capture runs, which is the only step this session never got to validate end to end.

Housekeeping performed before closing: all working .pcap files were deleted from the dockresearch account's home directory on azul (the originals are archived under re/captures/ in this repo), and the dockresearch local account was disabled (Disable-LocalUser) per the original session's own instruction to disable it once not actively in use. It was not removed (Remove-LocalUser) in case a follow-up session needs a fast re-enable rather than recreating the account from scratch; removing it entirely remains the user's call for a later cleanup pass.
