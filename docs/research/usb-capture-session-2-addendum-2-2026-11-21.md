## Second addendum: service-restart correlation, DP Alt Mode ruled out, WinUSB attempt and recovery

### Service stop/restart correlation test

Stopped USBDisplayService and killed USB Display.exe cleanly while a capture ran (`usbcap-azul-writetest-2026-11-21.pcap`, 60.4 MB, 139s), then restarted the service alone (without relaunching the app) and the dock's video resumed on its own. This is itself a useful finding: USBDisplayService, not the tray app, is the actual video driver; the app is a companion UI.

Across the whole stop/restart cycle, device 24's USB traffic (the ~34 KB/s constant-rate channel flagged as the leading video-channel candidate in the first addendum) never changed at all — no gap, no dip, nothing. Initially this looked like evidence against device 24 being video. Revised reading: the dock's "Connecting Signal..." screen is plausibly a UI overlay gated by a separate heartbeat/control-plane channel (the JSON-RPC heartbeat found on MI_00, likely driven by the service), shown whenever that control-plane heartbeat lapses, independent of whether the underlying data channel is still running. Under that reframe, device 24's constancy through the cycle is consistent with (not contrary to) it being the real video feed running continuously underneath the overlay. Still unconfirmed either way — no raw content proof, just behavioral consistency.

The two write-attempts made during this capture (`HidD_SetOutputReport` with Report ID 1 on MI_00, ID 2 on MI_01) produced zero real USB-level transactions — confirmed by scanning the capture for SET_REPORT control setup packets (0x21/0x09) with zero true matches (a raw 2-byte string search found superficial "21 09" byte sequences but none were real control transfers in context). This confirms `HidD_SetOutputReport` was failing inside the Windows HID class driver stack before ever reaching the USB wire — consistent with it expecting one complete report by the declared length, when the device may only accept smaller raw interrupt-level fragments directly, which the standard HID API does not expose a way to send.

### DisplayPort Alt Mode ruled out

User pointed out the dock is connected directly to azul's motherboard USB-C port, not through an external hub/dock-of-docks — prompting a check of whether the video bypasses USB entirely via a hardware DP Alt-Mode tunnel (which would fully explain why no USB capture has ever shown real video traffic). Checked via `Get-CimInstance Win32_VideoController`: azul has a device named **"extension Graphics Adapter"**, PNPDeviceID containing `VID_ACTIONSMICRO&PID_EXTENSION_VIRTUAL_DISPLAY_0001` — a legitimate Windows Indirect Display Driver (IddCx) installed by Actions Microelectronics. This creates a virtual GPU output that Windows renders a desktop to, which USBDisplayService then captures (almost certainly via Desktop Duplication API) and transports to the dock. This **rules out DP Alt Mode conclusively** — the architecture is a genuine software-compression-over-USB pipeline, not hardware tunneling, so the video traffic should be findable on the USB bus somewhere; it is not bypassing the protocol stack electrically. A `"Generic Monitor (HDMI Extender)"` monitor entity distinct from the user's three real BenQ monitor instances is almost certainly the render target behind this virtual adapter — worth confirming directly in a future session.

### WinUSB/raw-URB attempt on MI_01 (user executed via Zadig)

Plan: since `HidD_SetOutputReport` fails inside the HID class driver before reaching the wire, bypass HID entirely by rebinding MI_01's driver to WinUSB (via Zadig, since a custom INF attempt failed Windows' driver-signature requirement and azul has neither test-signing mode nor the Windows SDK's signing tools installed) and talk to it with raw `WinUsb_ReadPipe`/`WinUsb_WritePipe` calls instead.

- User downloaded Zadig, used **Options → List All Devices**, correctly identified `1DE1 F201 01` (the `01` suffix is the interface number — confirmed this distinguishes MI_00 from MI_01 in Zadig's list) and replaced its driver with WinUSB. Confirmed via `pnputil`: `MI_01` showed `Class=USBDevice`, `Driver=oem106.inf` (the Zadig-installed package), `Status=Started`. The dock's screen dropped to "Connecting Signal..." immediately, as expected (USBDisplayService could no longer use that interface).
- Wrote a WinUSB P/Invoke probe tool (`winusb_probe.ps1`) to enumerate device interfaces and call `WinUsb_Initialize`. Found the dock's interface (`usb#vid_1de1&pid_f201#84832a9f#{guid}`) — `CreateFile` succeeded, but `WinUsb_Initialize` failed with error 8 (`ERROR_NOT_ENOUGH_MEMORY`) — and the **same error occurred across essentially every other WinUSB-bound device on the system**, including unrelated vendors (Realtek, etc.). This pattern means the bug is in the P/Invoke code itself (likely a struct layout or calling-convention mismatch), not specific to the dock or to the Zadig driver swap, which otherwise worked correctly. Not resolved this session — noted as a real but generic tooling bug, not a finding about the device.
- Attempted to revert via Zadig's own restore function; it hung (process `zadig-2.9.exe` unresponsive, UI beeping on interaction). Killed it via `taskkill /F` and reverted the driver directly instead: `pnputil /delete-driver oem106.inf /uninstall /force` — reported "System reboot is needed to complete uninstall operations" but the live device state immediately showed `Class=HIDClass`, `Driver=input.inf` (the correct original driver) — a partial/ambiguous success, as with the earlier "disable-device" incident this session.
- Restarting `USBDisplayService` alone was not enough to restore video (dock stayed on "Connecting Signal..."). Direct `pnputil /disable-device` on MI_01 then failed outright with **"Device is pending system reboot to complete a previous operation"** — confirming the driver-package removal had left a real half-applied state blocking further operations.
- **User physically disconnected and reconnected the dock**, which forced a full USB re-enumeration and cleared the pending state without an actual OS reboot. Confirmed via `pnputil`: `MI_01` now `Status=Started`, `Driver=input.inf`, no pending-reboot flag. `USB Display.exe` memory back to 158 MB (matches the known "actively streaming" signature). Video confirmed working normally by the user.

### Net result of the WinUSB attempt

No raw-URB access to the device was actually achieved — the P/Invoke bug blocked it before any real pipe read/write was attempted. The driver swap itself worked (Zadig correctly identified and rebound MI_01), demonstrating the mechanism is viable in principle for a future attempt, but the tooling needs a fix (or a from-scratch rewrite, ideally tested first against a known-good WinUSB device to isolate the bug from any dock-specific behavior) before it's worth trying again. The recovery, while eventually clean, required a physical unplug/replug — this should be treated as an expected cost of this specific technique (Zadig swap → generic `pnputil /delete-driver` revert) going forward, not a one-off fluke.

## Current full status (end of session)
- Dock is healthy and streaming normally. All four composite interfaces (MI_00/01/02/04) `Started` with correct original drivers.
- Leading video-channel hypothesis remains: device 24 (USBPcap address, ep1 interrupt, 64-byte reports, ~531 pkt/sec, high-entropy, 68% duplicate rate on static image, unaffected by the service stop/restart cycle) — still unconfirmed by direct content proof.
- DisplayPort Alt Mode is definitively ruled out — confirmed software pipeline via IddCx virtual display driver + USBDisplayService capture/encode/transport.
- MI_00 is confirmed to be a JSON-RPC heartbeat/status channel (Report ID 1), not video.
- Raw-URB/WinUSB access was attempted but blocked by a generic P/Invoke bug in this session's tooling, not by anything device-specific; the underlying technique (Zadig driver swap) is viable and worth retrying once the tooling bug is fixed.

## Options going forward
1. **Fix and retry the WinUSB raw-URB route.** Debug the `WinUsb_Initialize` P/Invoke failure against a known-good test device first (isolate the bug from the dock entirely), then redo the Zadig swap on MI_01 (or MI_00) and attempt real `WinUsb_ReadPipe`/`WinUsb_WritePipe` calls. Highest potential payoff (direct raw access to the exact bytes crossing the wire, both directions) but highest remaining effort, and each attempt costs a physical unplug/replug cycle to recover cleanly.
2. **Capture with USBPcap running before `USBDisplayService` starts**, to catch the actual channel-establishment handshake. Every capture taken across both sessions started after the service was already running in steady-state; we have never actually seen how the video channel (whichever one it is) gets set up. Low risk, no driver changes, just capture timing — cheap to try next.
3. **Pursue the device-24 content-replay test as originally proposed**: extract its captured payload sequence from a static-image capture (already have one, `dev24_static_sequence.json`) and attempt to resend those exact bytes via a *correctly working* raw-URB write, watching for the dock to show a stale/frozen image. This is really step 1's payoff once the tooling bug is fixed, not a separate option — listed separately because it's the actual decisive test if the raw-URB route is restored.
4. **Try the simpler non-destructive OS-level identification first**: use ETW tracing (`logman`/`tracelog`) on `USBDisplayService.exe` to see which file/device handles it opens and how much it reads/writes to each over time — this is a read-only diagnostic (no driver changes, no disconnect risk) that could directly identify which interface carries the bulk of the data without needing raw USB access at all.
5. **Stop the live-system poking entirely and go back to static analysis**: continue the Ghidra disassembly of `USBDisplayService.exe`/`USB Display.exe` (started in an earlier session for the installer) specifically to find the code path that opens the video-carrying handle and read off its exact HidD/WinUsb/CreateFile call and target path from the binary — this answers the question with certainty and zero live-system risk, at the cost of more time spent reading disassembly instead of poking hardware.

Recommended order if continuing: 4 first (cheap, safe, likely narrows it down fast), then 5 if 4 is inconclusive (also safe, more certain but slower), with 2 as a cheap add-on whenever a capture is running anyway. Save 1/3 (WinUSB raw-URB) for last, given tonight's cost-per-attempt (a physical replug) and the still-unresolved tooling bug.
