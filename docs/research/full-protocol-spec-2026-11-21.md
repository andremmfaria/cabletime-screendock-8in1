# CABLETIME ScreenDock (CB09W) — full USB protocol reference spec (2026-11-21)

This document consolidates everything known about the CABLETIME ScreenDock's USB composite-device protocol as of this pass, combining the already-confirmed video-channel findings (summarized, not re-derived — see the cited docs for full detail) with new findings from extending the Ghidra static analysis of the real Windows driver binaries (`USB Display.exe`, `USBDisplayService.exe`) to the remaining interfaces and vendor functions. Method: pyghidra against the already-analyzed Ghidra projects at `re/win_real/*_ghidra/` (analysis was cached from the prior session, so this pass's scans completed in seconds rather than the ~15 minutes a cold analysis takes), using the same string-literal-to-containing-function and symbol-table cross-reference pattern as the prior pass. New scripts: `re/pyghidra_win_gui3_strings.py` through `re/pyghidra_win_gui7_json.py`, `re/pyghidra_win_svc3_strings.py`.

The device is `VID_1DE1&PID_F201`, a composite USB device with (at minimum) five interfaces, MI_00 through MI_04.

## MI_00 — control / heartbeat (confirmed, high confidence)

- Path: `VID_1DE1&PID_F201&MI_00&COL01`. HID Report ID **1** (`interface_number + 1`).
- Role: JSON-RPC control/heartbeat channel. Two confirmed JSON-RPC methods, both newly found this pass by scanning `USB Display.exe`'s string table for `jsonrpc`/`heartbeat`/`params` literals (prior pass had only found the `heartbeat` string inside `USBDisplayService.exe`):
  - `{"jsonrpc":"2.0", "method": "heartbeat", "params": {"session-id": "<tick-count>"}}` — sent periodically, confirmed in both `USBDisplayService.exe` (`FUN_0040407c`, prior pass) and independently in `USB Display.exe`'s own `RemoteControl::Do_Heartbeat` / `RemoteControl::USBHeartbeatThread` methods (this pass). The GUI app runs a second, redundant heartbeat loop on the same interface, alongside the service's.
  - `{"jsonrpc":"2.0", "method": "reset"}` — **follow-up pass, actively traced, direction still unresolved:** this exact string literal has **zero code references** anywhere in `USB Display.exe` according to Ghidra's own reference-manager analysis (checked directly — `getReferencesTo()` on its address returns an empty list), unlike the heartbeat strings right next to it in the same string-table cluster, which do have live referencing functions (`RemoteControl::Do_Heartbeat`, `RemoteControl::USBHeartbeatThread`). This pass also fully decompiled the adjacent static-initializer block (`0x00461a01`–`0x00461cbc` in `USB Display.exe`) that constructs the real JSON-RPC method-name table used by this binary's generic command-builder framework (the one found via `"jsonrpc"` string cross-references) — it builds ~30 genuine method names (`heartbeat`, `common.get_device_description`, `common.set_device_description`, `common.get_service`, `common.request_stream[_fullscreen]`, `common.cancel_request_stream`, `common.answer_request_stream[_fullscreen]`, `common.enable_control`, `common.disable_control`, `common.disconnect_all`, `common.get_ota_config`, `common.set_ota_ready`, `media.volumeDown`, `media.volumeUp`, `media.getVolume`, `media.setVolume`, `app_tx_mouse_icon_change`, `app_tx_mouse_coordinate`, `app-launched`, `projection-request-with-tx`, `notify-projection-started`, `request-ota`, `projection-request-cancel-with-tx`, `dismiss-any-dialog`, `notify-button-pressed`, `notify-button-long-pressed`, `notify-app-no-pairing-info-found`, `request-ota-data`, `notify-ota-started`, `notify-ota-progress`, `notify-ota-complete`, `common.data_passthrough`) — **`"reset"` is not among them.** The same check against `USBDisplayService.exe`'s string table (broad scan for `reset`/`HEARTBEAT_TIMEOUT`) also found no code paths touching it, only generic TCP/socket-library strings (`network reset`, `connection reset`, `ResetEvent`) that are unrelated boilerplate. **Updated assessment (medium-high confidence): the `"reset"` JSON-RPC string is most likely dead/vestigial content inherited from the shared EZCast/EZMira codebase this vendor's products are built on** (the same codebase that contributed the already-identified `notify-button-pressed`/`spacedesk` dead code noted elsewhere in this doc), not an active call path exercised by this ScreenDock build. Whether it is sent host→dock, dock→host, or never at all in any shipped firmware/driver combination remains open — no executing producer or consumer was found in either binary.
  - No other JSON-RPC methods were found anywhere in either binary's string table. In particular, no `"brightness"`, `"power"`, `"edid"`, `"resolution"` (as a JSON-RPC method, as opposed to the many *unrelated* generic "resolution" log/EDID-decode strings — see MI_01 section below) or similar control methods exist on this channel. **If the dock's physical brightness/power buttons or EDID exchange are reported to the host at all, it is not via MI_00's JSON-RPC** (see "Open questions").
- Wire framing: shared with MI_01, see next section.

## MI_01 — video (confirmed, high confidence; two header fields newly traced, semantics still open)

Full prior writeup: `docs/research/video-channel-resolved-2026-11-21.md` and `docs/research/windows-real-driver-ghidra-analysis-2026-11-21.md`. Summary, not re-derived: path `VID_1DE1&PID_F201&MI_01&COL01`, Report ID 2, opened by `USBUtil::FindDisplayHIDPath` (logs "HID Display device found"), fed H.264 (SPS/PPS once, then per-frame slices) by `EZDisplayTransmitter::SendHID`. Live capture of a real 833-second session confirms the framing byte-for-byte: 23,959 real video messages, sizes 67–255,983 bytes, H.264 Annex-B NAL units starting at header-relative offset 16.

### Wire frame layout (confirmed, unchanged from prior pass)

| Offset | Size | Field | First chunk | Continuation chunk |
|---|---|---|---|---|
| 0 | 1 byte | Report ID (`interface_number + 1`) | 2 | 2 |
| 1–4 | 4 bytes, BE uint32 | total message length | populated | 0 |
| 5–8 | 4 bytes, BE uint32 | metadata field A | populated | 0 |
| 9–12 | 4 bytes, BE uint32 | metadata field B | populated | 0 |
| 13–15 | 3 bytes | zero padding | 0 | 0 |
| 16+ | up to 4080 bytes | payload chunk | H.264/JSON data | raw continuation data (no header at all beyond the Report ID byte) |

Live-capture values (23,959 messages, cold-start session): field A is always `0`; field B is always `327680` (`0x00050000`).

### New this pass: data-flow trace of field A / field B

Traced the producer chain for `SendHID`'s `param_4`/`param_5` (= field A/B) through three functions not decompiled in the prior pass:

- `EZDisplayTransmitter::SetVideoBuffer` (`FUN_0052923f`) is called once per captured/encoded frame. It holds a 25-slot ring buffer (`% 0x19`) of frame-buffer-descriptor structs. After calling the active encoder object's vtable slot `+0x08` (the encode call — its result is stored at ring-slot offset `+0x10` and used elsewhere as a "frame ready" / output-size flag), it makes **two more vtable calls with no arguments**, on vtable slots `+0x0c` and `+0x10` of the same encoder object (`*(int*)(this+0x104)`, i.e. whichever of `AMFEncoder`/`QSVEncoder`/`H264Encoder` was selected by `H264EncoderFactory::RequireEncoder`), and stores their return values at ring-slot offsets `+0x14` and `+0x18` respectively.
- `FUN_00529791` (called from `EZDisplayTransmitter::send_thread`, `FUN_00529a68`) pulls the oldest ready ring-buffer slot and copies its `+0x14`/`+0x18` fields out through its own `param_6`/`param_7` output pointers.
- `send_thread` passes those two output values straight through as `SendHID`'s `param_4`/`param_5` (field A/B).
- The SPS/PPS send (the very first message of a session) explicitly passes `param_4=0, param_5=0` — consistent with the live capture's SPS message also showing field A/B as part of the same always-0/always-327680 pattern seen on every other message, which means **the two argumentless getter calls return the exact same values for the SPS/PPS send as for every subsequent per-frame send in this particular encoder configuration**.

**Assessment (medium confidence, not fully resolved):** the two getters are called once per frame, which would be consistent with a PTS/timestamp pair or a per-frame flag — but the live-capture evidence (constant across 23,959 real messages spanning 813 seconds) rules that out: these are not a sequence number or timestamp. They read as **fixed encoder-instance properties that happen to be queried on a per-frame cadence but don't vary with frame content or time** — e.g. a capability/profile flag and a format/timebase constant that's set once at encoder init and simply returned unchanged thereafter.

**Follow-up pass: the vtables and both getter bodies are now found and decompiled.** The prior pass's symbol search failed because it looked for symbol names literally containing `"<ClassName>vftable"` concatenated — Ghidra actually stores these as a bare symbol named `vftable` *inside* a namespace matching the C++ class (recovered from RTTI), so the right query is "symbols named `vftable` whose parent namespace is `H264Encoder`/`AMFEncoder`/`QSVEncoder`", not a substring match on the combined name. Doing that turns up all three real vtables (`AMFEncoder::vftable @ 0x0091b9b4`, `QSVEncoder::vftable @ 0x0091ba98`, `H264Encoder::vftable @ 0x0091bb6c`), confirmed directly against each class's constructor (e.g. `H264Encoder`'s constructor, `FUN_005499c5`, contains the literal assignment `*param_1 = H264Encoder::vftable;`). Dereferencing slots `+0x0c`/`+0x10` in all three and decompiling the targets shows **an identical, trivial pattern in every class** — plain one-line field-accessor getters with no computation at all:

| Class | slot `+0x0c` getter | slot `+0x10` getter |
|---|---|---|
| `AMFEncoder` | `return *(this+0x80);` | `return *(this+0x84);` |
| `QSVEncoder` | `return *(this+0x34);` | `return *(this+0x38);` |
| `H264Encoder` (x264 SW) | `return *(this+0x530);` | `return *(this+0x534);` |

Tracing each class's `InitEncodeH264` constructor-style init function shows these per-class offsets are written exactly once, from that function's `param_2`/`param_3` (e.g. `H264Encoder::InitEncodeH264`, `FUN_00549ab9`, does `*(this+0x530) = param_2; *(this+0x534) = param_3;`, and the x264-software path forwards those same stored fields straight into `x264_picture_alloc(pic, csp, *(this+0x530), *(this+0x534))` a few lines later) — strong, structural evidence (identical across all three otherwise-unrelated encoder classes) that these are a **`GetWidth()`/`GetHeight()`-style accessor pair** (or a very close sibling of one, e.g. encode-buffer dimensions) returning values latched once at encoder initialization and simply read back unchanged on every subsequent frame — exactly matching the "fixed per-session properties on a per-frame query cadence" behavioral read above.

**Final pass: raw x86 disassembly of the ambiguous call site, and of the entire getter→wire-byte data path, closes most of this out but surfaces a real, unresolved numeric contradiction (reported honestly rather than forced to a tidy answer).** Bypassing the decompiler entirely and reading the actual instructions:

- The getter bodies themselves are exactly as trivial as the decompiler said, confirmed at the instruction level: `H264Encoder::vftable+0x0c` → `FUN_00549947` = `MOV EAX,[ECX+0x530]; RET` (two instructions, no shift, no arithmetic). `+0x10` → `FUN_0054994e` = `MOV EAX,[ECX+0x534]; RET`. There is no hidden `SHL`/`OR` inside either getter.
- The "ambiguous 8-argument call against a 6-stack-argument prototype" is now explained, not just flagged: at `EZDisplayTransmitter::PrepareH264Encoder`'s vtable-slot-0 call site (`0x0052ab03`–`0x0052ab1e`), the raw disassembly shows exactly 8 `PUSH` instructions before `CALL dword ptr [EAX]`, with `ECX` loaded from `[EBX+0x104]` (the encoder object) just beforehand — i.e. a real `__thiscall` dispatch. Separately disassembling `H264Encoder::InitEncodeH264` (`FUN_00549ab9`, confirmed as the literal target of `H264Encoder::vftable` slot 0 by direct vtable-slot memory read) shows its own prologue only ever reads `[EBP+0x8]` through `[EBP+0x1c]` — six stack dwords (`param_2`..`param_7`). Mapping the 8 pushes to callee stack slots (last-pushed = first-param, standard `__thiscall`/`cdecl` stack order) shows the **last 6 pushed values are what `H264Encoder::InitEncodeH264` actually consumes; the first 2 pushed values (`[EBP-0x64]` = `0x26`/`0x1c`, `[EBP-0x5c]` = `0x17`/`0x12` — quality/bitrate-shaped constants, not dimensions) are pushed but never read by this backend.** This is a genuine, intentional asymmetry in the vendor's own generic vtable-dispatch code (the call site is shared by `AMFEncoder`/`QSVEncoder`/`H264Encoder`, and presumably one of the hardware backends' `Init` does consume all 8), not a decompiler artifact — closing the "ambiguous 8 vs 6 argument" open item with concrete evidence.
- Tracing the 6 consumed arguments back through the same raw disassembly (cross-checked independently against the high-level decompiler's own variable naming, which agrees) shows `InitEncodeH264`'s `param_2`/`param_3` (destined for `+0x530`/`+0x534`, i.e. exactly the two getters above) are fed by `PrepareH264Encoder`'s **own incoming width/height-shaped arguments** (`EDI`/`[EBP+0x8]` and the duplicate stored at `[EBP-0x68]`, read into `ESI` just before the call) — on the normal/untouched code path (the resolution-downscale and 1080p-override branches both provably not taken for a sub-threshold 1280×720 request), these evaluate to the panel's nominal **1280 / 720**, not to `0` / `327680`.
- The remainder of the data-flow chain from the getters to the wire bytes was independently re-disassembled end to end and is a **lossless, transform-free pass-through at every step**: `SetVideoBuffer` (`FUN_0052923f`) stores the two getters' raw return values into ring-slot `+0x14`/`+0x18` with a plain `MOV`, no arithmetic. `FUN_00529791` copies ring-slot `+0x14`/`+0x18` straight out through its `param_6`/`param_7` output pointers (`*param_6 = local_24; *param_7 = local_20;`), again no transform. `send_thread` (`FUN_00529a68`) forwards those two output locals unchanged into `SendHID`'s `param_3`/`param_4`. `SendHID` (`FUN_0052b624`) forwards them unchanged into the real wire-builder `FUN_00525cca`. That function's raw disassembly (`0x00525dde`–`0x00525e2c`) shows the header bytes at offsets 9–12 are built purely from four `SHR`-by-`0x18`/`0x10`/`0x8`/`0` extractions of the raw 32-bit `param_4` value — a textbook big-endian byte-split, **not** a value-transforming shift. **This conclusively rules out the "field B = width shifted left by 8 at send time" hypothesis**: no such shift-left instruction, and no literal `0x50000`, exists anywhere in this entire call chain, in the getters, or in the wire-builder.

**Net result of the static-analysis pass:** the structural claim (two argumentless per-encoder-instance getters, set once at init, read every frame, encoder-class-polymorphic but always `GetWidth()`/`GetHeight()`-shaped) is confirmed at the instruction level, and the previously-ambiguous call site is fully explained (8 pushed, 6 consumed, by design). But the concrete numeric claim — that these specific getters' return values are what appear as field A/B on the wire — looked contradicted by that same trace, since the values fed into `+0x530`/`+0x534` traced to ≈1280/720, not 0/327680, with every later hop provably value-preserving and no shift/arithmetic found anywhere in the chain.

**Resolved empirically, superseding the static-analysis contradiction above.** Rather than chase this further with a live debugger, ran a live multi-resolution test directly against the device instead: captured USB traffic on azul while cycling through every resolution option Windows offered for the dock's virtual display, plus landscape/portrait orientation changes, across two capture sessions totaling ~490 seconds and 9 distinct resolution/orientation combinations. Result: **field A is `0` in every single combination tested, with zero exceptions** (confirmed genuinely unused/reserved, not resolution- or orientation-dependent). **Field B fits a clean, exact formula with zero exceptions: `field B = target display width in pixels × 256`** (equivalently `width << 8`). Cross-validated two independent ways: (1) `fieldB / 256` always lands exactly on the real encode width for every tested combination (1280, 1920, 1600, 900, 960, 800, 720 — the last two being the width-after-rotation values for portrait orientation, confirming the dock encodes the *rotated* width, not the original landscape width, when the display is rotated); (2) directly decoding each H.264 SPS NAL's own embedded width (which independently confirms the same values, accounting for the standard H.264 macroblock-padding rounding — e.g. a true width of 900 pads to a coded SPS width of 912, since SPS dimensions must be multiples of 16 — field B tracks the *true* nominal width, not the padded coded width). Critically, **field B tracks width only, never height**: at one point in the live test the height cycled through 960→800→720 while the width stayed at 1280 throughout, and field B stayed at exactly `327680` (1280×256) unchanged through all of it. Height is carried purely by the standard H.264 SPS NAL itself (with ordinary macroblock padding/cropping), not by this vendor header at all.

**Practical conclusion for a Linux driver supporting a resolution picker:** fully solved, no debugger needed. Set `fieldA = 0` always; compute `fieldB = target_width * 256` for whatever width is being encoded (post-rotation width, if rotated); let the H.264 encoder (`libx264`/`ffmpeg`) handle height and all coded-size padding/cropping the normal way. The earlier static-analysis contradiction (tracing suggested ~1280/720 feeding the getters, not 0/327680) remains unexplained as a *code-level* mechanism, but is no longer practically relevant — the live, reproducible, zero-exception empirical formula is what actually matters for building a working implementation, and it is now fully established.

**On the GPU-vendor question (new this pass):** `H264EncoderFactory::RequireEncoder` (`FUN_0054247d`) contains **no GPU-vendor/WMI/DXGI adapter-detection logic of any kind** — it simply probes `QSVEncoder::IsSupport` then `AMFEncoder::IsSupport` (both via each class's vtable slot `+0x18`) and falls back to the software `H264Encoder` (bundled libx264) if neither hardware path reports itself usable. **No `NVENCEncoder`-style class, and no NVIDIA/NVENC API import, exists anywhere in this binary.** The single "NVIDIA" string found in the whole executable (`FUN_004e3ae5`) is an unrelated vendor-ID-to-name lookup table used by the bundled `edid-decode`-style EDID-parsing code (sitting alongside `"AMD"`, `"ASUS"`, `"Apple"`, `"Dolby"`, `"HDMI Forum"`, etc. — i.e., EDID/CTA-861 vendor IDs, not GPU-encoder selection). **Conclusion: on a host with an NVIDIA-only GPU and no Intel iGPU (so no QSV) and no AMD GPU (so no AMF) — matching azul's live system info — `RequireEncoder` would fail both hardware checks and fall back to the software `H264Encoder` (libx264) path.** This is a new, concrete finding: the live encoder on azul is almost certainly the **software x264 path**, not a GPU-hardware encoder, and definitely not NVENC, which this codebase has no support for at all.

## MI_02 — USB Audio Class (newly investigated this pass: confirmed out of scope for vendor code)

- Enumerates as "USB Display Audio (HDMI 1)" using the stock Microsoft `wdma_usb.inf` USB Audio Class driver (per background/prior-session finding — not re-derived here).
- **New finding this pass:** exhaustive string-table scans of both `USB Display.exe` and `USBDisplayService.exe` for `MI_02`, `audio`/`Audio`/`AUDIO`, `USB Audio`, and related keywords turn up **zero references tied to actually handling this device's audio interface**. The only "audio" hits in `USB Display.exe`'s string table are:
  - Generic Intel Media SDK / AMF audio-codec plumbing strings (`MFXAudioENCODE_*`, `MFXAudioDECODE_*`, `audio_decoders`, `audio_encoders`) — boilerplate from the bundled hardware-media-SDK libraries, not evidence of vendor audio-handling code being exercised.
  - Generic `edid-decode`-library CTA-861 audio-block descriptor text (`"Audio Data Block"`, `"HDMI Audio Data Block"`, `"Supports Dolby TrueHD..."`, etc.) — this is the string table of a well-known open-source EDID-parsing tool statically linked into the binary for generic monitor-capability parsing, unrelated to the dock's own audio path.
  - `"Virtual Audio Render/Capture Device (WDM) - spacedesk Speaker/Microphone"` and the matching `VID_DATRONICSOFT&PID_SPACEDESK_VIRTUAL_AUDIO_*` GUID strings — these come from **spacedesk SDK code reused inside this binary** (spacedesk is a separate, unrelated virtual-display product; its IddCx/virtual-audio code appears to have been inherited wholesale when this vendor built their virtual-display driver stack on top of it — this also explains the previously-unremarked `ALMonitorIddCx`/`ALInputManagerHid`/`ALThreadFrameBufferHook` class names seen in earlier passes). This is dead/inherited code for the ScreenDock's own purposes, not evidence of a custom vendor audio protocol.
- **Conclusion (high confidence, by absence):** MI_02 carries audio purely via the stock Windows USB Audio Class driver; no vendor application code on the Windows side reads, writes, or configures it in any custom way. This matches the "exists but is a standard class device" expectation from the background brief.

## MI_04 — USB Mass Storage (newly investigated this pass: confirmed out of scope for vendor code)

- Enumerates as "USB Mass Storage Device" using the stock Microsoft `usbstor.inf` driver (per background/prior-session finding — almost certainly the virtual CD-ROM gadget serving the Windows installer, not re-derived here).
- **New finding this pass:** the same exhaustive string-table scans (`MI_04`, `storage`/`Storage`/`STORAGE`, `cdrom`/`CDROM`, `USBSTOR`/`usbstor`) found **zero hits in either binary**. No vendor code anywhere references this interface at all — not even indirectly (e.g. no installer-launch-detection logic, no "please wait while drivers install" string tied to a CD-ROM path).
- **Conclusion (high confidence, by absence):** MI_04 is a pure firmware-level gadget (virtual CD-ROM presenting the installer) that the OS's native mass-storage driver handles with zero vendor software involvement once Windows itself mounts and (if autorun is used) launches from it. Neither of the two analyzed executables ever looks at it again after that point.

## Other vendor-protocol surfaces checked this pass

- **EDID / display-configuration exchange:** extensive EDID-related strings exist in `USB Display.exe`, but all of them belong to the string table of a generic, openly-licensed `edid-decode`-style library (CTA-861/DisplayID block-parsing diagnostic text) used for standard EDID parsing of whatever monitor the OS hands it — there is no code found that reads or writes EDID bytes over MI_00 or MI_01 as a custom vendor exchange. The built-in screen's EDID (1280×720 @ 60 Hz, per `docs/specs.md`) is most likely exposed to Windows through the IddCx virtual-display-adapter path (consistent with prior-session findings and the spacedesk-derived code noted above), not through a vendor HID message.
- **Brightness / power buttons (extended, live-tested this pass):** no JSON-RPC method, HID report pattern, or log string tying either button to host-side code was found in either binary. The `"notify-button-long-pressed"` / `"notify-button-pressed"` strings seen in the GUI's string table belong to the EZCast/EZMira remote-control feature set (for that product line's physical remote), not the ScreenDock's own brightness/power buttons. `USBDisplayService.exe`'s only button/power-adjacent code is **standard Windows service power-event handling** (`SERVICE_CONTROL_POWEREVENT`, `PBT_POWERSETTINGCHANGE`, `GUID_MONITOR_POWER_ON`) — i.e., the service reacting to the *host PC's* sleep/wake/monitor-power transitions, not anything from the dock's hardware buttons.

  **Live test performed:** captured USB traffic while physically pressing the brightness button twice and the power button twice (power press cycling the dock fully off then on), ~1s apart each. Confirmed no clean HID report (JSON-RPC or otherwise) correlates with any individual press. However, the capture shows **four distinct, clustered GET_DESCRIPTOR re-enumeration storms** (~106.7s, ~108.7s, ~111.0–112.3s, ~113.2–113.3s in that capture), each simultaneously re-enumerating the *same* ~10-11 USB addresses — every device behind the dock's internal hub chip (`VID_1A40&PID_0801`, see "Hub / multi-port passthrough" below), not just the dock's own composite function. Four clusters for four button presses is a plausible match (not confirmed with frame-exact certainty — the capture doesn't carry a direct "button pressed" marker, only the resulting bus-level effect).

  **Revised conclusion:** button presses most likely do **not** send a software-level report to the host at all (consistent with zero vendor code found), but they do appear to cause a brief, crude hardware-level effect: a power-rail or reset blip on the dock's entire internal USB hub, which cascades into re-enumerating every downstream device, not a clean per-button signal. Plausible explanation: the buttons are wired through the same small MCU that also manages USB power delivery to the internal hub chip, so any button press causes a momentary glitch on that rail. This is a live-observed, higher-confidence finding than the prior absence-based inference, though the precise causal link (which exact press caused which exact cluster) was not nailed down frame-by-frame.
- **Resolution negotiation:** `DisplayUtil::ChangeResolution` and related logging (`"Change resolution: deviceName--"`, `"Supported resolution: "`, `"H264 encoder not support resolution: "`) exist and are clearly real, but operate on the OS-level virtual-display-adapter resolution list (IddCx), not on a custom vendor-to-dock wire message — i.e., "resolution negotiation" here means Windows' display settings UI picking from a mode list the IddCx driver advertises, not the dock being asked over USB what resolutions it supports. No evidence of the dock's actual physical panel resolution (fixed at 1280×720 per spec) being queried or negotiated over HID.
- **Hub / multi-port passthrough (resolved, high confidence, by live topology check, refined further this pass):** no string or symbol referencing `hub`, downstream-port management, or per-port device enumeration was found in either `USB Display.exe` or `USBDisplayService.exe` — confirming the vendor's own software is not port-aware at all, exactly as expected for a question that's purely hardware-level. Directly confirmed on the physical device instead, in two stages:

  **Stage 1 (USB-A ports):** a USB headset plugged into the dock's USB-A passthrough ports enumerated as a fully independent device (`VID_1B1C&PID_0A42`), and `DEVPKEY_Device_LocationPaths` showed it sitting on hub `VID_1A40&PID_0801` (Terminus Technology) at different downstream ports depending on which physical USB-A connector was used (port 4 via the USB-C-passthrough test's USB-A adapter, port 3 when plugged into the dedicated USB-A 2.0 connector directly) — the same internal hub chip hosting the dock's own `VID_1DE1&PID_F201` composite device (port 2). A port-by-port scan via `IOCTL_USB_GET_NODE_CONNECTION_INFORMATION_EX` confirmed that hub exposes exactly 4 downstream ports: port 1 (unidentified, nothing plugged in during this pass), port 2 = the dock's own composite device, port 3 = USB-A 2.0 connector, port 4 = seen occupied by the same headset when connected via a different physical path (see Stage 2 for why).

  **Stage 2 (USB-C data passthrough, newly tested this pass):** a phone (Google Pixel 8 Pro, `VID_18D1&PID_4EE1`, MTP mode) plugged into the dock's USB-C data passthrough port did **not** appear on any port of the Terminus hub at all. Its `DEVPKEY_Device_LocationPaths` placed it at a *sibling* location one tier up (`...USB(3)#USB(3)`) from the Terminus hub itself (`...USB(3)#USB(2)`) — i.e., on a different port of whatever hub the Terminus hub's own upstream connection attaches to, which turned out to be a **Genesys Logic hub** (`VID_05E3&PID_0610`), not dock-internal Terminus silicon.

  **Conclusion: the dock's internal USB topology is two-tier, not a single flat hub.** The Terminus `VID_1A40&PID_0801` chip hubs together the dock's own composite device and the USB-A passthrough ports (lower-speed/shared traffic). The USB-C data passthrough port is most likely a **true electrical pass-through** of the upstream USB-C cable's SuperSpeed lanes, wired straight through without going through any dock-internal hub chip at all, which is why it appears as a sibling of the Terminus hub rather than a child of it — a common real design for "hub with passthrough" USB-C docks, where only the shared/lower-speed ports get actively hubbed and the passthrough port is a dumb electrical relay needing full bandwidth. The Genesys Logic hub it sits behind is most likely one tier further upstream (plausibly azul's own motherboard/case-level hub, consistent with Genesys-vendor hubs appearing repeatedly elsewhere in this investigation's captures, unrelated to the dock itself) rather than anything inside the dock. Windows' native USB hub/class drivers handle all of this transparently with no vendor protocol involvement, matching the "no vendor code is port-aware" code-level finding exactly.

  **Stage 3 (LAN/Ethernet and the remaining Terminus port 1, this pass):** also checked the dock's Ethernet function — a `Realtek USB GbE Family Controller` (`VID_0BDA&PID_8153`, the RTL8153 chip) is present on the system regardless of whether a LAN cable is plugged in (Ethernet PHY chips enumerate on USB independent of physical link state). Its location path (`...USB(3)#USB(4)`) places it as a **third sibling** of the Terminus hub on the same upstream Genesys hub, exactly like the USB-C data passthrough — so LAN also bypasses the Terminus hub entirely, confirming the pattern: the Terminus hub only handles the dock's own composite device and the two USB-A ports; everything needing full/dedicated bandwidth (USB-C data, Ethernet) gets its own direct sibling connection upstream instead. This also rules out both of the two most obvious guesses for the Terminus hub's still-unidentified port 1: it can't be Ethernet (confirmed elsewhere, as a sibling) and it can't be the USB-C PD power input (power delivery negotiates over CC pins at the physical layer and never enumerates as a USB device at all, so it could never appear in a hub port scan regardless of which port). That leaves the **SD/TF card reader as the best-supported remaining candidate for Terminus port 1** (medium confidence, not directly tested — no SD/TF card was available this pass): a card reader with no card inserted plausibly presents nothing at all on the bus, consistent with port 1 reading as fully empty (`VID=0000/PID=0000`, as opposed to "a device present but idle") rather than every other identified port, which show their real VID/PID immediately whether or not they're actively doing anything. Since the spec lists SD and TF as two separate slots but only one Terminus port remains unaccounted for, they likely share a single combined SD+TF reader controller chip that presents as one USB mass-storage device when either slot has a card in it. Confirming this definitively just needs an SD or microSD card physically inserted and the same hub scan re-run.

  **Resulting full topology (confirmed so far):** upstream Genesys Logic hub (`VID_05E3&PID_0610`) → port 2: Terminus hub (`VID_1A40&PID_0801`) → [port 1: SD/TF reader, inferred, untested; port 2: dock's own `VID_1DE1&PID_F201` composite device; port 3: USB-A 2.0; port 4: USB-A 3.0]; Genesys port 3: USB-C data passthrough (direct electrical relay); Genesys port 4: Ethernet/RTL8153 (direct electrical relay). The Genesys hub's own further upstream connection and the USB-C PD power-input path were not traced further this pass.

## Open questions

- ~~Which vtable slots `+0x0c`/`+0x10` resolve to and what class owns them.~~ **Resolved** (see "New this pass: data-flow trace of field A/B" above): real `vftable` symbols exist per-class under RTTI namespaces (`AMFEncoder::vftable`, `QSVEncoder::vftable`, `H264Encoder::vftable`), and both slots decompile to trivial field-accessor getters fed by `InitEncodeH264`'s constructor-time parameters in all three classes — most likely a `GetWidth()`/`GetHeight()`-style pair.
  ~~Whether the "ambiguous 8-argument" call-site rendering is a decompiler artifact.~~ **Resolved this pass, by direct raw-disassembly of the call site and of `H264Encoder::InitEncodeH264`'s own prologue:** it is not an artifact. `PrepareH264Encoder`'s vtable-slot-0 call genuinely pushes 8 stack dwords (confirmed instruction-by-instruction at `0x0052ab03`-`0x0052ab1e`), but `H264Encoder::InitEncodeH264` (the real target for this device, confirmed by direct vtable-slot memory read) only ever reads the last 6 of them (`[EBP+0x8]`-`[EBP+0x1c]`); the first 2 pushed values are quality/bitrate-shaped constants (`0x26`/`0x1c`, `0x17`/`0x12`) that this backend simply never touches. This is a real, shared-dispatch-site asymmetry (the same call serves `AMFEncoder`/`QSVEncoder` too, which may consume more args), not decompiler confusion.
  **Still genuinely open, and now sharper than before — a confirmed contradiction, not just a gap:** raw disassembly of every single hop from the two getters down to the actual wire bytes (`SetVideoBuffer` → `FUN_00529791` → `send_thread` → `SendHID` → the low-level HID writer `FUN_00525cca`) shows a byte-for-byte, transform-free pass-through at every step — including confirming there is **no shift-left-by-8, no literal `0x50000`, and no arithmetic of any kind** anywhere in this chain or inside the getter bodies themselves (both are literally `MOV EAX,[ECX+0x530/0x534]; RET`, nothing else). That means the two getters' raw return values are exactly what ends up as field A/B on the wire, with nothing in between to explain a discrepancy. Yet tracing the one call site that actually sets those return values (`PrepareH264Encoder`'s call into `InitEncodeH264`) — by two independent methods, a raw register/stack trace and the decompiler's own variable naming, which agree — shows the values fed in are `PrepareH264Encoder`'s own width/height-shaped arguments, which evaluate to the panel's nominal 1280/720 on the normal code path, not 0/327680. `327680 = 1280 × 256` remains a numeric coincidence with no supporting code found anywhere, not a confirmed derivation. Closing this for real now needs either a live debugger breakpoint on `H264Encoder::InitEncodeH264` (`0x00549ab9`) or on either getter (`0x00549947`/`0x0054994e`) during an actual capture session to read the true runtime values, or a careful re-walk of `PrepareH264Encoder`'s dozen-plus untested conditional branches against the device's actual live config-field values (not assumed ones).
- ~~Which concrete encoder class is actually live on azul given its NVIDIA GPU, and whether an NVENC path exists.~~ **Resolved this pass:** no NVENC-capable class exists anywhere in this binary; `H264EncoderFactory::RequireEncoder` has no GPU-vendor-detection logic at all, it just probes `QSVEncoder::IsSupport` then `AMFEncoder::IsSupport` and falls back to the software `H264Encoder` (libx264) otherwise. On an NVIDIA-only host with no Intel iGPU and no AMD GPU (matching azul), this means the live encoder is almost certainly the software x264 path, not any GPU-hardware encoder.
- **The `"reset"` JSON-RPC method's actual trigger/effect, and its direction (host→dock vs. dock→host).** Upgraded this pass from "found only as a string literal" to "actively ruled out of every JSON-RPC dispatch path found in either binary" (see MI_00 section above) — Ghidra's own reference analysis shows zero code references to the string's address, and the ~30-method dispatch table this pass fully enumerated via the adjacent static-initializer block does not include it. Working theory: dead/vestigial string inherited from the shared EZCast/EZMira codebase, not wired into this ScreenDock build. Still genuinely open: no producer or consumer was found in either binary, so direction and trigger remain unknown; a live-capture watch for a `"reset"` JSON-RPC message during a dock power-cycle or host-sleep/wake event would be the way to close this out empirically if it matters for a future goal.
- ~~Whether the dock reports anything at all for its brightness/power buttons.~~ **Resolved, live-tested:** no clean per-button report found (see "Brightness / power buttons" above), but button presses do cause a real, crude hardware-level effect — a brief power/reset blip on the dock's entire internal USB hub, observed as four re-enumeration storms matching four actual button presses in a live capture. Still open: the precise causal mapping of which press caused which exact storm was not nailed down frame-by-frame.
- ~~Whether the dock's internal hardware uses a USB hub chip for the passthrough ports.~~ **Resolved** (see "Hub / multi-port passthrough" above, three stages of live testing): yes — Terminus `VID_1A40&PID_0801` hubs the dock's own composite device (port 2) and the two USB-A ports (port 3 = USB-A 2.0, port 4 = USB-A 3.0); port 1 is inferred (not directly tested) to be a combined SD/TF card reader, since Ethernet and USB-C-PD power-input have both been ruled out as candidates for it. USB-C data passthrough and Ethernet both bypass the Terminus hub entirely as direct electrical relays sitting on a separate upstream Genesys Logic hub. Only remaining gap: physically confirming port 1 by inserting an SD/microSD card and re-scanning (none was available this pass).
- **`EZEncodeEnc*` functions in `ImgEnc.dll`** remain undecompiled (noted but deprioritized in the prior pass since the real H.264 encoder was found to live in `USB Display.exe` instead); likely unused by this device given that finding, but not proven unused.
- **`avformat-57.dll`'s role** remains unconfirmed (not imported by any of the three previously analyzed binaries); not reinvestigated this pass.
